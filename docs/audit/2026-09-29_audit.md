## 1. Product, implementation stage, and scope

### What this product does

Mantle is an unreleased distributed object-store/file-system design whose primary intended interface is S3. It targets agent-produced data and deployments from one laptop to a fleet. A laptop is intended to run the same stack as one node in one cell. A region contains independent cells behind an endpoint and a cell map; adding cells supplies capacity and isolates failures.

Inside a cell:

- **Name** metadata maps ordered bucket/object keys to versions, upload parts, configuration and lifecycle state.
- **File** metadata maps random file identities to ordered extents and wrapped encryption keys. A completed multipart object is a file of part files.
- **Block** metadata maps block identities to chunk locations and maintains reverse location rows.
- Metadata ranges have separate Raft groups; groups on one metadata device share a log and its group commits.
- Gateways seal plaintext in 64 KiB AES-GCM segments, group sealed segments into blocks, replicate or Reed–Solomon encode them, and write chunks directly to volumes.
- Writes proceed chunks → Block → File → Name. The Name commit is the object write's linearization point. Reads go down that graph, verify stored data and encryption tags, and reconstruct from other chunks when needed.
- Chunk volumes use append-oriented data segments, a circular index log, checksummed records, alternating superblocks, a cleaner and a scrubber.

The architecture explicitly says **Raft groups and erasure-coded stripes do not span cells**. Global scale therefore means many bounded stacks and a correct routing/migration layer. A single worldwide Raft group is not the stated architecture.

### What exists today

The executable offers disk inspection/calibration, storage/crypto/EC benchmarks, and a durability estimator. The repository contains substantial protocol, chunk-store, metadata, shared-log and range-replica libraries and simulations. The gateway PUT library/state machine has landed; serving and distributed drivers remain to be integrated.

A production metadata engine, actual S3 serving integration, production transport, topology-aware placement, repair/rebalancing, orphan-chunk reconciliation, and cells/migration remain explicitly planned in [STATUS](../STATUS.md). They are **release prerequisites**, not discoveries that implemented features are mysteriously broken. Neither a complete running cluster nor Meta-scale performance was demonstrated by this audit.

### Safety properties used to judge the code

1. An acknowledged chunk or metadata update survives the required failure model, or is reported as damaged and repaired; it is never silently reclassified as an unacknowledged write.
2. A replica never forgets or regresses durable term/vote state, and each group's persistence respects submission order.
3. Nothing reachable from a committed version or an active upload is reclaimed.
4. Retries, overlapping sweep workers, leadership changes, stale routes and ownership transfers preserve those properties.
5. Correctness does not depend on a grace period making an ownership race unlikely.
6. Admission bounds include queued, deferred, executing and response work, in bytes as well as counts.
7. Storage choices follow actual path capabilities and measurements, while durable acknowledgement remains correct on every supported backend.

These follow [CLAUDE.md](../../CLAUDE.md), [metadata design](../design/metadata.md), [chunk-store design](../design/chunk-store.md), [Raft-log design](../design/raft-log.md), and [replica design](../design/replica.md).

## 2. Confirmed Standards defects

Evidence labels distinguish **Reproduced** from **Source-confirmed**. A reproduction test that passes by asserting faulty behavior proves the defect; it does not mean the implementation is correct. P1 means resolve before production use; P2 means material correctness/resource work; P3 means a narrower edge or contract problem.

### S01 — P1: log recovery silently removes acknowledged history after frame-header corruption

**Continuation status: partial.** The interior/header schedule below was corrected in 40a6ef5. bc193fa adds independently placed persist records and an uncertainty/election fence for confirmed lost frames. Seven focused log/range regressions passed at 08bd9a4. A new deterministic probe nevertheless reproduces an acknowledged entry disappearing with no uncertainty before its confirmation becomes durable. S16 separately exposes loss of a damaged-group fence on another restart.

**Location:** [recover.rs:50](../../crates/log/src/recover.rs#L50), identity checks at 53–57, highest-segment scan at 289–320, boundary erasure at 393–421. **Evidence: Reproduced.**

A bad frame magic/format or mismatched log/incarnation/nonce returns Found::End. Only Found::Invalid runs the search for a later valid frame. Consequently a corrupt interior header is treated as an ordinary log tail even when intact later frames prove it belonged to acknowledged history.

**Reproduction:** put creation frame sequence 0 and four successfully acknowledged update frames 1–4 in one segment; flip the magic bit of frame 1 at offset 8192; reopen. Open succeeds with frames=1, damaged=[], and no group view. All four acknowledged updates disappear. Recovery then overwrites the supposed tail boundary.

This can erase terms/votes as well as object metadata. Raft assumes durable state remains durable; silently restarting a replica with forgotten votes is a consensus-safety problem, not simply a missing entry.

**Fix:** authenticate and inspect later aligned candidates on every unexpected termination of a potentially live frame, including damaged identity headers. Distinguish proven stale-incarnation records from corrupt identity bytes. Refuse or quarantine acknowledged damage and recover from peers before rejoining; preserve evidence rather than zeroing it.

**Regression:** independently damage every header field and payload/CRC field at interior and final boundaries; include valid later frames, reused slots and reopen after the attempted recovery. The existing payload-damage test is insufficient.

**Round-three residual at 08bd9a4:** [writer flush](../../crates/log/src/writer.rs#L574) persists the frame and its record, publishes it, and answers success. That record confirms the preceding flush. The current frame is confirmed by a later successful frame or a separate [idle/close confirmation](../../crates/log/src/writer.rs#L156). For an unconfirmed damaged frame, [recovery](../../crates/log/src/recover.rs#L715) restores only a later term/vote, with no entries, start, proposals or uncertainty mark. This window is disclosed in the design; disclosure does not satisfy the audited acknowledgement/repair contract.

The SimFile probe establishes and confirms entry 1, reopens, then permits exactly the next frame write, persist write and successful flush using `PowerCut { ops: 3 }`. Entry 2's `log.write` returns **Ok**; subsequent confirmation cannot write. Crash preserves flushed bytes; a stored bit flip then damages that last frame. Reopen succeeds with **last=1, uncertainty=None, term/vote=(2,2), damaged=[]**. The probe uses the real writer/recovery and passes by asserting that faulty result. It does not refute ordinary crash-only durability.

The consensus implication is source-derived, not a newly executed three-member simulation: A/B may commit an entry, A becomes partitioned, and B recovers through this schedule with a shortened log. A later-term stale candidate C can use the B/C quorum without B's missing-entry election guard, because no uncertainty mark exists. Retaining B's old term/vote prevents a repeated vote in that term; it does not preserve the acknowledged log's up-to-date comparison in later terms.

The stated approximately one-flush exposure is also not guaranteed: [commit](../../crates/log/src/writer.rs#L305) returns without a frame when all submissions are refused and no sweep runs; the idle receive returns arriving submissions before confirmation. Continuous refused traffic can suppress the timeout indefinitely without producing a successful confirming frame. This timing extension is source-confirmed, not separately reproduced. Track confirmation against an absolute obligation independent of input arrival. For an exact contract, durably establish the prefix authority before acknowledging, or prove safe handling of every ambiguous unconfirmed prefix. An eventual/periodic marker only changes exposure probability. Preserve the tested liveness of genuinely unacknowledged tails while resolving their ambiguity safely.

### S02 — P1: frame overflow lets a newer same-group update commit before an older one

**Continuation status: corrected in 40a6ef5; the current same-group capacity-deferral regression passed. The description below preserves the original failing schedule.**

**Location:** [writer.rs:211](../../crates/log/src/writer.rs#L211), especially 233–235. **Evidence: Reproduced.**

The writer's seen set normally keeps a group's second update out of the current frame. When the first update cannot fit, the writer defers it and removes that group's reservation. A smaller later update for the same group can now fit and commit ahead of it. The deferred older update commits next.

**Reproduction:** use 4 × 4096-byte segments; queue a group B update with 10,000 payload bytes, group A's earlier 3,000-byte update with HardState(term=1,vote=1), and A's later small HardState(term=2,vote=2). Every submission is acknowledged. A first becomes durable at term/vote 2/2 and then finishes at **1/1**.

**Fix:** keep the group reserved after capacity deferral and preserve per-group FIFO across held work and newly received work. Do not rely on callers never batching several updates; the shared log exposes asynchronous submissions and states this ordering invariant itself.

**Regression:** interleave groups and heterogeneous sizes around exact frame limits, entry replacement/compaction and held-queue arrivals; assert ordering both before and after reopen. Include a monotonic hard-state assertion where required by the caller contract.

### S03 — P1: the log's bounded channel conceals an unbounded deferred backlog

**Continuation status: corrected in a27792a; the all-unanswered admission regression passed. Aggregate node/device/transport budgets remain separate work.**

**Location:** [writer.rs:119](../../crates/log/src/writer.rs#L119), accounting at 175–181, held work at 211–235; admission in [lib.rs:298](../../crates/log/src/lib.rs#L298). **Evidence: Reproduced.**

Channel accounting is released on dequeue, before completion. The writer drains the channel without a batch count/byte ceiling and moves additional same-group updates into held. That work is outside admission accounting. Producers can keep filling the channel while the writer completes only one update per group per flush. An uninterrupted producer can also prolong the drain and delay the commit itself.

**Reproduction:** with queue_submissions=2 and deterministic gated flushes, accept 12 submissions while only five commit; seven remain outstanding. Continuing the schedule increases the outstanding count despite the nominal two-submission bound.

**Fix:** reserve combined queued + held + executing count and encoded-byte budgets until completion. Bound gathering independently, including container/record overhead for tiny or empty entries. Return typed backpressure when the combined budget fills. Schedule groups fairly so one hot range cannot consume the device's backlog.

**Regression:** run sustained same-group and mixed-group producers behind delayed flushes; assert high-water bounds and eventual commit progress without sleeps that merely make the race less likely.

### S04 — P1: a recoverable log refusal permanently strands a replica's outstanding Ready

**Continuation status: corrected in a27792a; a held Ready resumes after compaction in the current regression. The synchronous driver still delays networking and independent groups; see §§5/11.**

**Location:** [replica.rs:316](../../crates/range/src/replica.rs#L316), persistence at 329. **Evidence: Reproduced.**

drive consumes Ready and then uses ? on write_waiting. A nonfatal Backlog, Full or TooLarge returns without retaining the Ready for retry or otherwise putting the adapter into an explicit terminal state. RawNode still knows a Ready is outstanding and rejects further operations.

**Reproduction:** one-member leader, valid log group_entries=2, applied index 1; queue two proposals before drive. drive returns Log(Backlog(1)). Compaction succeeds and frees enough room, but subsequent tick fails with “an operation while a ready is out,” and drive fails with “a ready asked for while one is out.” There is no adapter retry path.

**Fix:** compact and validate admission before taking Ready where possible; retain staged Ready through recoverable capacity refusals; validate proposal/message byte limits against the log's frame and retention bounds. Fatal failed writes/flushes must fence/recover, not be retried as ordinary backpressure.

**Regression:** force each nonfatal refusal, free its limiting resource, and demonstrate progress with the same pending work. Separately demonstrate fencing after actual durability failure.

### S05 — P1: chunk recovery can checkpoint away healthy acknowledged data after a transient bad read

**Continuation status: corrected in 27b2389; the exact transient-read test passed. Unverified last records are retained/reported rather than deleted.**

**Location:** [recover.rs:154](../../crates/chunk/src/recover.rs#L154), fragment removal at 175–180, recovery checkpoint in [volume.rs:218](../../crates/chunk/src/volume.rs#L218). **Evidence: Reproduced.**

The last batch may have been unflushed, so recovery verifies its data. A failed verification is used as evidence that the indexed fragment should be removed. That conflates a torn, unacknowledged tail with damage or a transient read error affecting an acknowledged record. The recovery checkpoint makes the removal permanent.

**Reproduction:** acknowledge a 9,000-byte put, close, inject a read-only bit flip in its durable payload, and reopen. Open succeeds, reports unflushed_dropped=1, and stat returns no chunk. Clear the read fault: all original durable bytes are healthy, but read returns NotFound. A second reopen still has no chunk.

**Fix:** preserve indexed identity/provenance for ambiguous damaged tail data; quarantine/report damage, retry according to a bounded policy or repair, and only undo data whose unacknowledged status is actually established by the protocol. If the current record format cannot distinguish cases, strengthen the persistence/recovery protocol rather than silently choosing data deletion.

**Regression:** combine acknowledged/unacknowledged crash tails with transient and stored corruption, final-batch relocations, deletes and repeated reopen. Preserve existing crash-tail guarantees while preventing loss of repairable identities.

### S06 — P1: calibration and benchmark scratch handling can overwrite or delete preexisting files

**Continuation status: Corrected in 1bfb22b. Exclusive randomized scratch ownership is acquired only after creation; calibration-failure and existing file/link regressions passed.**

**Location:** [calibrate.rs:265](../../crates/disk/src/calibrate.rs#L265), Scratch cleanup at 228–229, nonexclusive creation in [file.rs:229](../../crates/disk/src/file.rs#L229); same pattern in [bench_log.rs:91](../../crates/mantle/src/bench_log.rs#L91). **Evidence: Reproduced.**

A deterministic .mantle-calibrate-<pid> path is opened with create(true), not exclusive creation. Cleanup ownership is acquired before open and unconditionally deletes the path. An existing file, reused PID, symlink, or concurrent library calibration can therefore be overwritten/deleted. Even a failure before useful calibration work can delete data the operation never created.

**Reproduction:** place a file containing customer-data at the predicted scratch path; request a plan with small=0. Calibration returns InvalidInput, but the preexisting file is gone.

**Fix:** use randomized, exclusive creation in the requested directory, with platform-appropriate protection against following existing links. Acquire cleanup ownership only after successful creation. Carry that owned handle through caching fallback and cleanup. Apply the same ownership rule to every benchmark scratch call site.

**Regression:** preexisting file/link, PID-like collision, simultaneous same-process jobs, open/preallocation/validation failure, and successful cleanup.

### S07 — P2: read admission occurs after allocating the requested output

**Continuation status: Corrected in 1bfb22b. Count/byte admission precedes output reservation; the buffered-byte regression passed. Large results still require an integrated bounded streaming path.**

**Location:** [volume.rs:479](../../crates/chunk/src/volume.rs#L479), reserve at 499, read gate at 501. **Evidence: Source-confirmed.**

read_into collects fragment metadata and reserves len bytes before entering the gate. Even a read that will immediately receive Busy can allocate its full result; waiting reads reserve before obtaining device service. Device-depth bounds therefore do not establish a process memory bound. Appended chunks can cover many fragments, so the output can greatly exceed one 8 MiB record.

**Fix:** acquire an appropriate read/byte budget before allocation, impose a maximum buffered result, and expose streaming reads for larger ranges. Account queued output, checksum-read buffers and fragment lists together. Use fallible reservation where a typed capacity failure is practical; do not let client-controlled size reach an unchecked allocation.

**Regression:** hold the device busy, submit bounded/waiting/refused reads of varying sizes, and assert allocated bytes remain within the advertised aggregate budget.

### S08 — P2: public zero-depth read settings can make reads wait forever

**Continuation status: Corrected in 1bfb22b. Config::check refuses unusable settings before IO; the exact regression passed.**

**Location:** [layout.rs:56](../../crates/chunk/src/layout.rs#L56), [read.rs:67](../../crates/chunk/src/read.rs#L67), waiting loop at 75–80. **Evidence: Source-confirmed.**

Reads::measured clamps depth to one, but the public fields allow Reads { depth: 0, waiting: 1 }. The configuration boundary does not reject it. No reader can become active, yet one can enqueue and park waiting for a turn that cannot ever be returned.

**Fix:** validate all operational configuration at format/open, including depth, nonzero batch limits, representable derived budgets and cross-field constraints. Prefer validated types/constructors where an invalid value cannot be useful.

**Regression:** reject zero depth without starting workers or I/O; table-test zero/overflow/incompatible values. A regression should establish immediate typed rejection, not contain an intentionally hanging worker.

### S09 — P2: the standard calibration ladder can exceed its backend's supported depth

**Continuation status: Corrected in 1bfb22b. The ladder stops at the selected backend limit and reports capped results; the exact regression passed.**

**Location:** [calibrate.rs:102](../../crates/disk/src/calibrate.rs#L102), ladder at 332–341; [measure.rs:137](../../crates/disk/src/measure.rs#L137). **Evidence: Source-confirmed.**

The standard plan permits max_read_depth=65535, but the portable measurement backend allows at most 256 workers. If throughput continues growing through depth 256, the next quadrupled point is 1024; the whole calibration fails and loses accumulated results.

**Fix:** bound the ladder by the actual selected backend's concurrency/resource support. Return the best measured point with an explicit “saturation not reached before cap” result. A future deeper async backend should advertise its real capabilities, not inherit a controller's theoretical queue size.

**Regression:** use a deterministic growing-throughput backend to force the 64 → 256 → 1024 transition; preserve valid measurements and a typed capped status.

### S10 — P2: measurement thread creation can panic despite the production no-panic policy

**Continuation status: Corrected in 1bfb22b. Fallible scoped worker startup is all-or-none; the injected partial-start regression passed. S12 concerns the separate volume-owner startup path.**

**Location:** [measure.rs:169](../../crates/disk/src/measure.rs#L169); also inspect scoped spawns in CLI benchmark paths. **Evidence: Source-confirmed.**

Scope::spawn panics when the OS cannot create a thread. Catching join results handles worker panics, not that spawn failure. Calibration can request hundreds of workers. Lints do not detect the semantic panic inside this otherwise ordinary standard-library call. [Rust's Scope::spawn documentation](https://doc.rust-lang.org/std/thread/struct.Scope.html#method.spawn) specifies this behavior.

**Fix:** use fallible Builder::spawn_scoped, return a typed worker-creation error, and join already-created workers on partial failure. A persistent bounded executor also avoids rebuilding the worker population for each measurement.

**Regression:** inject spawn failure behind the executor seam; verify typed error and complete cleanup. Expand panic-path review beyond explicitly named panic/unwrap calls.

### S11 — P3: zero-capacity buffers evade pool byte accounting

**Continuation status: Corrected in 1bfb22b. Empty buffers allocate nothing and are not pooled; real allocation is accounted, and the exact regression passed.**

**Location:** [buf.rs:128](../../crates/disk/src/buf.rs#L128), take at 323–339, retention/accounting at 361–364. **Evidence: Reproduced.**

A zero-capacity aligned buffer still allocates alignment slack, but the pool accounts capacity zero. Arbitrarily many returned zero buffers can accumulate even with a zero-byte limit. Current hot callers generally request actual blocks, so this is narrower than S03/S07.

**Fix:** make empty buffers allocation-free, avoid pooling them, or account actual allocation plus a free-buffer count bound.

**Regression:** retain many zero-capacity buffers at limit=0 and assert zero allocations or a bounded retained count.

### S12 — P2: failed partial startup can detach permanent volume owners

**Continuation status: corrected in 6e5aa5c.** The all-or-none startup owner and injected partial-start regression passed at 84cd9f5. The description below preserves the original failure.

**Location:** [volume.rs:229](../../crates/chunk/src/volume.rs#L229) through the optional scrubber spawn at 254–257; [clean.rs](../../crates/chunk/src/clean.rs#L89), [writer.rs](../../crates/chunk/src/writer.rs#L409). **Evidence: source-confirmed ownership/control-flow defect at the continuation cut; OS thread exhaustion was not induced.**

Writer and cleaner are started before the optional scrubber. If the third spawn fails, the function returns before constructing Volume and its shutdown owner. Dropping JoinHandles detaches the successful threads. Writer retains the cleaner wake sender; cleaner retains the writer submission sender; stopping remains false. Both receivers can therefore wait forever, keeping the device/index/buffers alive. Retrying under thread pressure compounds the leak and can establish another writer owner. Failure of the second spawn alone does not create this same permanent sender cycle.

**Fix:** establish a startup rollback guard before spawning. On later failure, set stopping, wake/join successful background owners, close producer handles, join writer and drop the backend before returning. Transfer the guard only after full startup. Add an injectable spawn seam; fail after each successful creation and assert all owners and backend resources are released. This enforces the documented owned-task/resource contract.

### S13 — P1: legal configured batches write index frames recovery silently discards

**Continuation status: corrected in 011466c.** Configuration and every generated frame kind share a validated bound; checkpoint segment/Put records stream through bounded frames. Seven existing focused boundary/reopen tests passed at 84cd9f5. The historical counterexample below is no longer claimed against that corrected source.

**Location:** [configuration checks](../../crates/chunk/src/layout.rs#L131), [geometry/frame sizing](../../crates/chunk/src/layout.rs#L220), [writer batching](../../crates/chunk/src/writer.rs#L454), [reader limit](../../crates/chunk/src/log.rs#L99), [checkpoint BEGIN](../../crates/chunk/src/writer.rs#L1250). **Evidence: reproduced on immutable 1bfb22b using an in-memory SimFile; no physical device was mutated.**

Config::check accepts nonzero batch_requests/batch_bytes, and Geometry sizes the log for the resulting largest frame without requiring it fit MAX_FRAME_BYTES. The writer can encode and durably publish a frame fitting that log. Recovery refuses a frame above its separate **4 MiB** limit and treats it as the end of the accepted frame stream. Valid configuration therefore permits acknowledged data to disappear on reopen.

The focused probe used a 128 MiB logical volume, 16 MiB segments, checksum_shift=12, batch_requests=max_fragments=70,000, batch_bytes=1 MiB and fragments_per_chunk=1. It deterministically preloaded the normal bounded writer channel using normal Queue::admit, then ran the unmodified Writer::run, avoiding 70,000 OS threads. **All 70,000 distinct one-byte writes returned Ok after flush/publication.** Their index frame was **5,320,704 bytes**. read_frame refused it solely for exceeding 4 MiB; Volume::open succeeded with **report.frames=0 and zero indexed keys**. This is a scheduling-seam counterexample, not a public throughput benchmark; the test passes by asserting faulty behavior. The standard 1,024-request batch is below this bound, but adaptive/wider configuration is precisely where the mismatch becomes dangerous.

The same unchecked bound affects checkpoint BEGIN: it puts all non-Free SegmentRecords into one frame, while only checkpoint Put frames are split. At 4 KiB alignment, 233,015 such segment records exceed the parser limit; legal small segments or large conventional volumes can reach that cardinality. This second path is source-confirmed, not separately reproduced.

**Fix:** derive and enforce a common frame/encoding/admission bound across format, configuration, batching, checkpointing and recovery, including header/padding/alignment and relocation/free/segment records. Reject impossible settings before IO or split frames using a validated checkpoint/publication protocol. Encountering an unsupported/damaged frame must never silently authorize erasing acknowledged history. Qualify every frame kind, generated-size boundary and reopen after publication; preserve full durable fences. Raising the parser constant alone does not fund its read memory/work.

**Artifact:** `/private/tmp/mantle-audit-frame-1bfb-ywskok50`; exact scratch test `volume::audit_frame_tests::audit_large_legal_batch_acknowledged_then_forgotten`, with source hash recorded in its evidence note. It is outside the source tree and is not shipped code.

## 3. Confirmed Spec defects

### B01 — P1: overlapping File sweeps reclaim data that a committed version still names

**Continuation status: corrected in f422d1e; the immutable-commit overlapping-sweep regression passed. Marks now remain through settling and disappear during reclamation.**

**Location:** [name.rs:993](../../crates/meta/src/name.rs#L993), release at 996–999; [sweep.rs:129](../../crates/meta/src/sweep.rs#L129), unmark command at name.rs:617. **Evidence: Reproduced through File/Block rows and simulated physical chunk inventory.**

The Name mark is treated as the entire proof that a file was handed over. A successful sweep settles the File queue and removes that mark. A second sweep can already have read the same queue row; its delayed check then sees the missing mark and interprets it as “never handed over.”

| Step | Sweep A | Sweep B | Persistent state |
|---|---|---|---|
| 1 | Reads unsettled file F | Reads the same F | Committed version references F; mark exists |
| 2 | Name check returns Held | Delayed | F still live |
| 3 | Settles F, then unmarks | Delayed | Queue row and mark gone; version still references F |
| 4 | Finished | Name check after deadline sees no mark | F is put on the release queue |
| 5 | — | Reclamation runs | Version survives; File, Block and chunk are deleted |

The defect survives the required “settle before unmark” order. A leadership takeover with delayed old work is enough; neither simultaneous active leaders nor a malicious gateway is necessary.

**Violated specification:** metadata's “none is released while something still names it” and its promise that two collectors across leader change only repeat safe steps.

**Fix:** persist an idempotent handover disposition, or use a durable sweep claim/generation with an authority that fences delayed release attempts. A Name-side authoritative owner check is another possible design if it covers versions, parts and adopted parts within a stated budget. Tombstones need a bounded retention lifecycle. A lease without fencing delayed actions does not solve the race, and a separate queue reread still has a time-of-check/time-of-use gap.

**Regression:** model two sweeps, delayed verdicts, leader takeover, retry after settle/unmark, and range movement. Run reclamation against the actual ownership graph and assert that every remaining Name/part reference resolves to existing bytes.

### B02 — P1: losing multipart compositions recursively delete live part files

**Continuation status: corrected in f422d1e; both original refused/retried-completion schedules now pass existing tests. Adoption is recorded at committed completion and Disown releases only the matching adopter’s parts.**

**Location:** [file.rs:150](../../crates/meta/src/file.rs#L150), failed-command release at [name.rs:636](../../crates/meta/src/name.rs#L636), completion retry at 1404–1410, adoption at 1477–1484; recursive descent at [reclaim.rs:248](../../crates/meta/src/reclaim.rs#L248). **Evidence: Two full-graph reproductions.**

A composite File is written with Target::File extents before Complete commits in Name. Those extents refer to part files that still belong to the upload. Failed or abandoned completion releases the composite; its reclaimer treats every child extent as owned and recursively deletes it.

There are two normal failure modes:

1. **Rejected completion:** active upload owns P. Composite C points to P. A conditional/invalid/stale completion is rejected and C is released. Reclaiming C deletes P's File, Block and chunk; the upload part row remains.
2. **Retry after successful completion:** C1 successfully commits and owns P. A retry constructs fresh C2, as the documented retry rule permits. Name recognizes the earlier result and releases C2. Reclaiming C2 deletes P, although the acknowledged C1 object still references it.

A gateway crash between preparing and adopting the composite exposes the same ownership ambiguity. Grace merely delays destruction.

**Violated specification:** every file has one referrer; completed parts remain object extents; no referenced data is released. Preparing a wrapper creates reachability but does not establish exclusive ownership.

**Fix:** give preparation, adoption, rejection and retry an authoritative durable ownership-transfer protocol. A losing wrapper must reclaim only its own rows. A winning wrapper must eventually reclaim the children it actually acquired. Consult/fence against the Name completion decision during cleanup, or use another proven transfer design. Independent cross-range reference increments/decrements are insufficient without an atomicity/recovery protocol. Recopying into fresh bytes is safe but changes the intended data-free completion cost.

**Regression:** failed condition, invalid part, expiry, gateway death, successful completion retry with a fresh wrapper, overwritten part, abort, leadership change and concurrent collectors. Include child files/blocks/chunks in the model. At the first-pass cut, completion properties maintained a test-side adopted map and lacked real failed-wrapper reclamation. f422d1e adds the actual adoption/disposition authority and expanded ownership schedules; focused losing/retry regressions now pass.

### B03 — P2: forgetting serial u64::MAX allows a supposedly exact-once command to run again

**Continuation status: Corrected in 1bfb22b. The spent final serial is refused before effect; the boundary schedule regression passed.**

**Location:** [session.rs:147](../../crates/meta/src/session.rs#L147), comparison at 78–83; wire serial acceptance at wire.rs:109. **Evidence: Reproduced.**

Eviction converts a forgotten serial to an exclusive low watermark with saturating_add(1). Forgetting MAX leaves low=MAX. check classifies only serial < low as forgotten; a retry of MAX without a retained answer is now New.

**Reproduction:** max_answers=1; apply serial MAX, then reordered MAX−1, evicting the first response; retry MAX. The same command creates two object versions at times 20 and 22. This is a boundary input, not a prediction that an ordinary client will issue 2^64 requests.

**Fix:** reject exhausted/reserved serials before any effect, or represent an inclusive forgotten watermark/exhaustion state without saturation. Preserve typed refusal and replay determinism.

**Regression:** reordered boundary serials, answer eviction, replay and session expiry; duplicates must never execute twice.

### B04 — P2: weak If-Match values are accepted for reads, writes and deletes

**Continuation status: Corrected in 1bfb22b. If-Match compares strongly and If-None-Match weakly; the exact comparison regression passed.**

**Location:** [conditional.rs:115](../../crates/s3/src/conditional.rs#L115). **Evidence: Reproduced; RFC mismatch confirmed, exact AWS weak-tag behavior unverified.**

The shared matcher strips W/ for both If-Match and If-None-Match. Given current ETag abc, If-Match: W/"abc" proceeds for GET, PUT and DELETE. RFC 9110 requires strong comparison for If-Match; weak comparison is appropriate to If-None-Match. [RFC 9110 §13.1.1](https://www.rfc-editor.org/rfc/rfc9110.html#section-13.1.1).

### B05 — P2: a CRC collision is accepted as an exact chunk retry

**Continuation status: corrected in 27b2389; the collision test passed. Queued/stored bytes are compared; an unverified stored copy is rewritten.**

**Location:** [writer.rs:630](../../crates/chunk/src/writer.rs#L630), equality/Done at 644–645. **Evidence: Reproduced.**

The retry check compares only length and CRC-32C. Those establish a corruption check, not byte identity. Distinct equal-length data with the same CRC receives success while the old bytes remain stored.

A deterministic reproduction found these eight-byte payloads:

    A = 95 fb df 74 c4 93 1b a0
    B = f0 80 c8 66 4e 34 ce 4a
    CRC-32C(A) = CRC-32C(B) = 5cac5032

put(key,A) succeeds; put(key,B) also succeeds; read(key) returns A. The API reports durable acceptance of B without storing B. Fresh random identities reduce exposure in normal gateway traffic, but the library's explicit exact-repeat contract is false.

**Fix:** compare stored/pending bytes on the duplicate path, or retain a sufficiently strong content identity and a clearly specified conflict policy. Pending same-batch retries need equivalent treatment. Do not replace the fast checksum used for routine corruption detection just to fix the rarer retry path.

**Regression:** use the fixed collision above, same-batch conflicts, sealed/unsealed fragments and true identical retries; different content must receive a conflict/exists result.

### B06 — P3, fixed during review: a malformed BlockSweep answer consumed its rejected request

**Location:** [sweep.rs:283](../../crates/meta/src/sweep.rs#L283), count validation at 286–292. **Evidence: Reproduced.**

**Regression:** short/long verdict vectors and mismatched answer types at each driver phase; then submit a valid response and demonstrate progress.

### B07 — P3: a valid-but-absent version marker contradicts the scan's fallback contract

**Continuation status: Corrected in 1bfb22b by aligning the local contract with ID-order resumption and testing a deleted marker between pages. The exact regression passed; real S3 edge-case conformance remains unrecorded.**

**Location:** [name.rs:1838](../../crates/meta/src/name.rs#L1838), implementation at 1859–1864. **Evidence: Reproduced internal contract mismatch; AWS behavior unverified.**

The public contract says an ID naming no version starts at the key's first version. The implementation checks only marker syntax, then seeks after its encoded order. A syntactically valid nonexistent marker can skip all of the key's actual versions and return End.

**Fix:** decide the intended external behavior, verify S3's edge case, and align the contract and implementation. If keeping the current promise, verify that the marker belongs to an actual version of this key before using its order.

**Regression:** deleted-version, different-key, valid-but-missing, null and malformed markers. Do not silently select an AWS rule based on the present comment.

### B08 — P2: PUT admission does not bound manifest or renewal work

**Location:** [Put::new](../../crates/gateway/src/put.rs#L271), retained blocks at 255, [renew_due](../../crates/gateway/src/put.rs#L692), final extent collection at 744; [File::Write](../../crates/meta/src/file.rs#L136). **Evidence: source-confirmed library admission/resource contract; no oversized transfer was executed.**

The constructor does not enforce the operation's length ceiling or derive/validate a maximum block/manifest count. The PUT retains every recorded block in a BTreeMap, scans all of them for renewals, can enqueue every due renewal in one turn, and collects all extents at the end. File::Write finally refuses more than 10,000 extents, after chunks/Block rows can already have been written. Two payload blocks in flight do not bound retained metadata, step CPU or renewal bursts.

This is not a maximum multipart-object incompatibility: the intended PUT/UploadPart ceiling is 5 GiB, while completed objects nest up to 10,000 part files. Preflight known length/layout/extent limits before expensive work; bound unknown-length streaming explicitly; reserve manifest/request capacity; index renewal deadlines and emit bounded batches with funded renewal progress. Test oversized refusal before chunk creation and legal maximum parts under delayed renewals/cancellation. Production HTTP admission is planned, but this public library should state and enforce its own bounds.

### B09 — P2: fixed-placement durability claims exceed the reduced failure model

**Location:** [generator](../../crates/ec/src/durability.rs#L205), [durability claim](../design/durability.md#L18) and degraded-placement assumption at 43. **Evidence: analytical counterexample and small exact placement-mask calculation, not observed object loss.**

The generator tracks only lost-chunk count and redistributes each degraded state's survivors evenly over all configured domains. Real survivors remain in their original surviving domains until repair/migration changes placement. Domain occupancy is therefore relevant state. The disclosed respreading assumption does not establish the claimed exact marginal probability for a fixed real placement.

For supported RS(6,3), place nine chunks as three per zone in three zones. With permanent zone-loss hazard λ and no independent chunk failure/repair, the first zone loss occurs at 3λ; after it, two nonempty zones remain and the next loss destroys readability at 2λ. Exact MTTDL is 1/(3λ)+1/(2λ)=5/(6λ). The reduced count model respreads six survivors as two per zone and reaches loss through a second 3λ event, giving 2/(3λ), **20% shorter**. A tiny exact mask/count calculation at λ=1/hour returned 0.8333333333333334 versus 0.6666666666666666 hours.

This example is conservative; it does not prove optimistic error or its direction for every accepted configuration. Either prove a conservative bound over accepted domain/repair policies and label the model accordingly, or retain occupancy with symmetry reduction. Validate small placements against actual domain loss, bursts, serial repair and repair placement. Solving/integrating the same reduced generator precisely tests numerical accuracy, not physical model equivalence. Qualify the annual exponential approximation when arbitrary zero/slow repair inputs violate rare-loss assumptions.

### B10 — P2: disk inspection claims zoned-write behavior without that backend

**Location:** [CLI disk report](../../crates/mantle/src/disk.rs#L41), [BlockFile](../../crates/disk/src/block.rs#L9), [geometry](../../crates/chunk/src/layout.rs#L162). **Evidence: source-confirmed user-visible capability mismatch.**

Correct the advertised claim and reject known unsupported host-managed formats before writes. A real zone backend needs discovered geometry, append results and crash-safe reset ownership. This sharpens §6's support gap; no new raw-device corruption was induced.

### B11 — P2: PUT cannot produce the specified SSE-C ETag

**Location:** [plaintext hash](../../crates/gateway/src/put.rs#L420), [ETag finalization](../../crates/gateway/src/put.rs#L473), [Keys/Body](../../crates/gateway/src/put.rs#L128), [encryption contract](../design/encryption.md#L109). **Evidence: source-confirmed helper/spec mismatch at 1bfb22b; no deployed SSE-C endpoint or external exploit was tested.**

PUT always updates MD5 over plaintext before sealing and publishes that digest as the Object/Part ETag. Its interface has no encryption-aware ETag policy, although the wrapping descriptor can identify a customer key. The design explicitly requires ciphertext MD5 for SSE-C. AWS requires an SSE-C ETag that is not the plaintext MD5; ciphertext MD5 is Mantle's own stronger design choice. [AWS Object semantics](https://docs.aws.amazon.com/AmazonS3/latest/API/API_Object.html).

Select ETag semantics from validated encryption mode. Retain plaintext MD5 where needed for Content-MD5 validation and the supported SSE-S3 profile; accumulate the specified ciphertext ETag after sealing for SSE-C. Keep plaintext checksum semantics intact, combine multipart part ETags under the selected mode, and test mixed/retried/replaced parts before claiming endpoint conformance. Account the resulting passes/CPU in the upload optimizer (§16.6).

## 4. Specific performance and efficiency investigations

These are source-grounded costs with proposed experiments, not invented speedup estimates. P01 was measured by instrumenting actual device calls; P02 has a diagnostic timing series. The remainder require representative release benchmarks.

### P01 — Range reads issue avoidable payload-prefix I/O

**Location:** [read.rs:134](../../crates/chunk/src/read.rs#L134).

The checksum block containing from is computed, but the device read starts at the record header and extends through the last requested checksum block. A tail read fetches every preceding payload block, even though only the requested checksum blocks are verified/returned.

**Measured:** a 4 KiB range at the end of an 8 MiB fragment caused **8,392,704 device bytes**, or **2,049×** the delivered bytes. The returned data was correct. Relative to one 64 KiB checksum unit, the unnecessary payload fetch is roughly two orders of magnitude.

Read/verify a bounded header/checksum table and then the requested aligned checksum spans, possibly using a bounded immutable-record header cache. Compare two small reads against a single longer sequential read on HDD; the preferred strategy should follow measured seek and transfer costs rather than a universal “two reads is always faster” rule. Benchmark random head/middle/tail ranges, full reads, mixed writes, cold/warm buffers and p99.

### P02 — Multipart cleanup is quadratic inside replicated apply

**Continuation status: f422d1e replaces the quadratic kept.contains scan with binary search over validated sorted parts. The diagnostic below describes the original cost; current release scaling measurements remain to be recorded.**

For each uploaded part, remove_upload searches kept with Vec::contains. Completing all N parts requires approximately N(N+1)/2 membership comparisons: **50,005,000 at 10,000 parts**, on each replica, in addition to row work.

| 1,000 | 4.2 ms |

### P03 — Coordinator learning repeatedly sorts and rescans the whole range directory

**Location:** [coordinator.rs:470](../../crates/meta/src/coordinator.rs#L470), learn at 487–492, covers at 500–506.

Learning R descriptors performs repeated linear ID lookup and sort; coverage walks rescan the full descriptor list. Large buckets and stale-route refreshes pay quadratic work. Coordinator state also has no intrinsic range-count ceiling. Bucket create/delete phases issue many sequential cross-range steps.

Consider bounded parallel requests within a coordinator phase while preserving all-gates/barrier and generation checks. Benchmark R=1/10/100/1k/10k with split/relearn/takeover schedules; optimize routing without weakening deletion fencing.

### P04 — Each command rewrites and searches the retained session response blob

**Location:** [session.rs:81](../../crates/meta/src/session.rs#L81), decode/eviction/re-encode at 136–150; response serialization in record.rs:883.

**Source boundary:** this cost describes immutable f422d1e and remains in 1bfb22b; serial exhaustion was corrected separately. The resolution ledger leaves P04 open.

A session with A retained answers imposes O(A) decode/search/serialization work per command and rewrites all retained response bytes. Vec::remove(0) shifts the remaining answers. Count bounds do not establish byte bounds, especially for verdict vectors and routing replies.

The same replicated entry can amplify this cost further: [apply](../../crates/meta/src/apply.rs#L31) checks and records each command independently; [Overlay reads](../../crates/meta/src/overlay.rs#L54) clone a value already rewritten earlier in that entry. With C commands and B average answer bytes, copied/decoded history work is O(C × A × B); as a fresh history grows before its answer cap, it can be O(C² × B). The entry's command-count cap does not establish a CPU-work or response-byte cap.

Decode each touched session once within an entry, process commands in their exact order, and serialize its final state once. Preserve retries, eviction watermarks, expiry indexes and atomic publication. A compact session header/frontier plus separate ordered answer rows is a further storage option, with per-session/range response-byte budgets. Benchmark 1/16/256 same-session commands and full histories; differential answers and final rows must match. A cache is an optimization of durable authority, not a replacement for it.

### P05 — Partly addressed during review: sweep grouping and repeated File extent scans

**Location:** [sweep.rs:263](../../crates/meta/src/sweep.rs#L263), [file.rs:233](../../crates/meta/src/file.rs#L233).

The initial snapshot grouped P due blocks from P files with linear searches through all earlier groups, giving O(P²) grouping. Concurrent work replaced this with BTreeMap grouping, addressing that component. Checking a file's membership still builds a set from all its extents each time; many pages of that file repeat the scan.

Keep the new map-based grouping bounded by the admitted page budget. Measure whether batching by file or a maintained membership index meaningfully reduces repeated extent work. Any cache/index needs byte bounds, invalidation and an authoritative ownership rule. Benchmark distinct-file pages, one maximal file across many pages, and foreground/collector contention.

### P06 — Scrubbing and cleaner selection repeatedly scan every segment

**Location:** [scrub.rs:246](../../crates/chunk/src/scrub.rs#L246), [clean.rs:214](../../crates/chunk/src/clean.rs#L214).

Every scrub window recomputes total live bytes by scanning all segment usage entries. With 1 MiB windows and 256 MiB segments, a roughly 20 TB device has about 75,000 segments and 19 million windows: order **10^12 segment visits per full pass** solely for this aggregate. This is a complexity estimate, not measured CPU utilization.

Cleaner selection also scans the whole usage vector; checking tried via linear membership compounds repeated victim searches. Usage read locks can interfere with publication by writers.

Maintain aggregate live bytes incrementally, and consider an occupied-window index and bounded candidate selection structures with generation validation. Preserve the current pacing of empty windows; avoid a faster implementation that spins on an empty device. Benchmark 1/10/100 TiB logical geometries, occupancy/fragmentation, near-full foreground p99, and cleaner work per reclaimed byte.

### P07 — Coalesce recovery and cold-log reads while retaining corruption proofs

**Location:** chunk [recover.rs:251](../../crates/chunk/src/recover.rs#L251); log [recover.rs:38](../../crates/log/src/recover.rs#L38); log entry reads in [lib.rs:429](../../crates/log/src/lib.rs#L429).

Use bounded sequential read windows/segments and coalesce nearby cold entries, verifying every existing identity/checksum. Capture immutable capacity once during open. Measure read calls, physical bytes and restart/catch-up time by entry size and medium, including corruption and reused slots.

### P08 — EC encode/decode/rebuild APIs copy more full shards than their callers need

**Location:** [ec/src/lib.rs:111](../../crates/ec/src/lib.rs#L111), rebuild at 146, data_chunks at 218.

encode materializes owned data shards and parity. decode copies present data shards and then gathers them into another output. rebuild constructs every data shard and then clones wanted shards; its missing-data path clones already copied present shards again. A request to recover one chunk can therefore allocate/copy substantially more than one chunk.

Investigate borrowed data-shard views, caller-owned output, reusable bounded encoder/decoder workspaces, and restoring only wanted originals where the library permits. Keep dependency panic boundaries and exact length/padding validation. A gateway's “two blocks in flight” is a logical pipeline bound, not a proof that its physical RSS is only twice one block: coding workspaces, parity, ready requests and network/TLS buffers must all be budgeted.

Benchmark healthy range GET without full decode, degraded GET, single-shard repair, full decode and mixed PUT/repair. Measure allocations and memory bandwidth alongside throughput; do not change the stored contiguous-shard layout casually.

### P09 — Calibration should measure the real workload and backend, not thread startup or reusable contents

**Location:** [measure.rs:154](../../crates/disk/src/measure.rs#L154), thread creation at 165–174, worker data at 218–246; [measurement design](../design/measurement.md).

The portable backend creates one OS thread per in-flight I/O and includes setup in elapsed measurements. ## 5. Raft and metadata service: concrete improvements and scale requirements

### 5.1 Overlap leader persistence, follower persistence and networking

At the continuation cut, [take_ready](../../crates/range/src/replica.rs#L445) puts leader-sendable messages into an output vector at 453; [persist](../../crates/range/src/replica.rs#L475) calls blocking write_waiting for each ordered part, and drive returns only afterward at 442, including apply work. The caller cannot send those messages during the local flush. The 64-Ready drive budget bounds count, not elapsed time/bytes/flushes. This serializes work that [replica design §3](../design/replica.md) intends to overlap. Preserve one outstanding Ready per group, while overlapping separate groups and exposing eligible leader messages; see §11.3.

Expose a staged interface: emit eligible messages, reserve/submit bounded persistence, suspend that Ready, then emit durability-dependent messages and advance after completion. Keep the ordering distinction explicit; follower vote/append acknowledgements must not be moved before required durability.

A device/node scheduler should stage multiple ranges before waiting for their shared flush, while reserving time for heartbeats, reads and apply. A serial loop calling the current blocking drive gives poor cross-range batching and lets one slow disk operation stall unrelated groups. Measure commit p50/p99, flush size, messages per commit, scheduler delay and election churn under mixed groups/RTTs before claiming gains.

The durable term/vote and ordered-log rules are foundations of Raft's safety. See the primary [Raft extended paper](https://raft.github.io/raft.pdf). Changing batching or transport must preserve those rules.

### 5.2 Enforce aggregate limits, not just per-range defaults

The wrapper constructs focal configuration from Settings but does not expose the core's full limits. Thousands of ranges each having individually bounded pending messages, unstable entries and reads can still exceed the node's memory.

Publish and enforce:

- Per-range proposal/append bytes, encoded command count, retained log bytes, outstanding reads and reply bytes.
- Per-device queued/held/executing persistence bytes, flush concurrency and foreground/background work.
- Per-node sums of range state, engine caches, sessions, snapshots, network/TLS buffers and coding workspaces.
- Per-tenant shares, weighted fairness and typed overload responses.

[S03](#s03--p1-the-logs-bounded-channel-conceals-an-unbounded-deferred-backlog) shows why accounting must survive dequeue. Snapshot, merge and reply buffers must acquire the same kind of durable budget ownership through completion/cancellation. A count ceiling alone does not bound memory: [name.rs:823](../../crates/meta/src/name.rs#L823) limits merge rows, [wire.rs:77](../../crates/meta/src/wire.rs#L77) limits commands, while row fields can have much larger encoded lengths. Bound actual bytes/work before cloning, encoding or proposing.

### 5.3 Make engine durability, applied index and compaction one proven contract

The model engine intentionally loses unflushed state. The future production engine must make rows, session outcomes, membership/descriptor state and the applied index recover coherently. Choosing RocksDB or another engine does not itself establish that contract.

Prove the ordering among durable Raft append, engine batch publication, engine flush, snapshot preparation and log truncation. Preserve the existing recovery reasoning for engines durable past a recovered commit. Failed apply must fence consistently; an ordinary command refusal must remain a replicated outcome rather than an adapter failure. Engine compaction and WAL/checkpoint work need foreground latency and disk-space budgets.

Run real-process kill/restart and corruption tests with the actual engine and filesystem, including full disks during compaction/snapshot. Do not substitute model-engine success for that validation.

### 5.4 Stream snapshots and large migrations

[replica.rs:480](../../crates/range/src/replica.rs#L480) obtains a complete row image and encodes another full byte image. [store.rs:147](../../crates/range/src/store.rs#L147) clones snapshot data; install decodes a further row image and sorts it. That is a workable small-model path, not a scalable snapshot mechanism.

The planned out-of-band engine-file path needs bounded concurrent streams, chunk integrity, resumability, cancellation/fencing on stale terms/generations, crash-safe publication and membership-aware catch-up. Snapshot transfer and learner rebuild must share repair/foreground bandwidth budgets. Test interrupted install, concurrent writes, two replacements, large ranges and near-full disks. Avoid publishing engine state from a snapshot whose corresponding log state cannot be made durable.

### 5.5 Retain ReadIndex correctness while reducing repeated work

check_quorum and pre_vote are already enabled; the simulation already uses ReadIndex and rejects unsafe reads in mutation tests. Those mechanisms deserve preservation.

Batch compatible ReadIndex confirmations and cache only at a proven term/applied-index boundary. A follower answering a read must establish the required current-leader authority and wait until local apply reaches the confirmed index. Any lease optimization needs an explicit clock/pausing model and fallback; it should not be enabled merely because it removes a round trip. Benchmark hot read ranges and election/partition boundaries with the linearizability checker.

### 5.6 Integrate fast track deliberately

The pinned core supports fast proposals, and Mantle already persists/restores proposal rows. Fast remains disabled; public proposer/displaced handling, durable group-mode identity and application qualification remain absent. The algorithm and ownership details in §11.5 are essential: Slates and Focal use different recovery/pruning rules, and their own measurements show profiles where fast is slower. Do not enable it by changing a boolean or transplanting one rule. Resolve the remaining durable-tail authority, account for every admitted proposal and measure real storage/tail/CPU/bandwidth results under the selected application contract.

### 5.7 Membership and metadata placement are separate from data-shard placement

The learner → catch-up → joint change → removal path is implemented and simulated. At scale, enforce failure-domain independence for metadata voters too, including their devices and shared logs. Three voters on one rack do not provide rack tolerance even if object chunks are distributed correctly.

Throttle simultaneous moves/replacements, bound learner lag and bytes, and prevent removal while the new replica lacks required durable state. Test loss during joint configuration, repeated leader transfer, multi-voter recovery and shared-log device failure. Define metadata quorum availability and data durability independently; one cannot compensate for the other.

### 5.8 Transport must defend the consensus scheduler

Mantle’s UDP-consensus/QUIC-bulk transport remains a plan. Slates’ actual council/root traffic now uses priority streams on its record sessions, while Focal uses Quinn; the comparative implementation and adoption analysis is in §§11/13. Define message authentication, node identity/authorization, replay handling, size limits, MTU strategy, retransmission and duplicate suppression. Large AppendEntries must not become unbounded fragmentation/reassembly work.

Partition transport queues by urgency and budget: a snapshot stream must not starve votes/heartbeats, and a flood of stale replies must not consume every CPU turn. Use actual packet-loss/RTT/bandwidth measurements, including slow receivers. QUIC or native async I/O is a mechanism, not evidence of an end-to-end throughput improvement.

### 5.9 Strengthen the failure model and invariants

Current deterministic simulation is valuable: real state-machine application, ReadIndex histories, membership replacement, failed writes/flushes and deliberately broken variants. Its small three-member/two-key workload and the collector models do not cover all compositions.

Retain the added header faults, same-group overflow order, recoverable Ready refusals, overlapping collectors and multipart adoption graphs. Expand to 1/3/5 voters; thousands of concurrently driven ranges; long partitions; duplicate/delayed messages; skew and clock steps; slow apply; snapshot pressure; multiple replacements; and full-disk/shared-device failures. Check safety after every action and liveness after faults stop. Keep failure seeds and mutation tests that demonstrate each invariant is observable.

## 6. Intelligent storage adaptation: detection must drive the actual I/O plan

### 6.1 Current state and the missing connection

The disk layer already identifies more than a generic “SSD”: media, interconnect, filesystem, logical/physical blocks, queue/transfer hints, write cache, FUA, zoned mode and composite members. It measures first-write/overwrite flush cost and throughput/depth, chooses measured read depth, and can choose prewriting. This is a substantial starting point.

However, calibration uses generic small/large workload shapes, and much of the identity is descriptive. Chunk/layout defaults still supply fixed segment, checksum, record and batch shapes; there is no complete profile translating capabilities plus representative measurements into every writer/cleaner/scrubber choice. **NVMe is a protocol/interconnect; SSD is a medium.** Treating them as mutually exclusive storage types obscures SATA SSD, NVMe SSD, remote NVMe and virtual-backed storage.

Introduce a persisted, versioned profile containing resolved path/backend identity, capabilities, mandatory alignment, measured workload curves, confidence/caps and the selected I/O/admission policy. Invalidate/revalidate it on device/firmware/backend/filesystem changes. Separate safe immutable format choices from mutable scheduling choices; changing a runtime batch size must not reinterpret old records.

### 6.2 Capability checks must precede formatting

Resolve a regular file to its actual backing storage; resolve a raw device as a device, not the filesystem containing its path. Use st_rdev for Linux device nodes and OS capacity APIs rather than regular-file length. Today Linux probing uses st_dev and can classify a /dev node through tmpfs; DeviceFile::len uses metadata.len, generally zero for Linux block nodes, so chunk open can skip superblock candidates. See [linux.rs:21](../../crates/disk/src/probe/linux.rs#L21), [file.rs:161](../../crates/disk/src/file.rs#L161), [volume.rs:639](../../crates/chunk/src/volume.rs#L639).

**Classification:** raw-device support gap. STATUS describes implemented directory/file paths, while the design intends raw/file equivalence. No raw disk was accessed or formatted in this audit.

Discover/enforce offset and buffer alignment, transfer ceilings, file-vs-device allocation behavior, flush/barrier semantics, topology and relevant zone geometry. Report the actual caching mode selected after direct-I/O fallback. Composite/virtual/network paths may conceal physical media; preserve Unknown and measure them rather than inventing a class from a device name.

A backend whose durability or write constraints are unsupported should receive a typed refusal before format. Direct I/O does not itself make writes durable.

### 6.3 Candidate strategies to validate by storage class

| Storage path | Candidate foreground strategy | Background/allocation strategy | Required evidence |
|---|---|---|---|
| NVMe SSD | Reusable/native async workers; measured QD; coalesce adjacent writes; bound batches by both bytes and latency; overlap independent ranges | Separate budgets for cleaner/scrub/repair; monitor sustained throttling and endurance; use discard only when supported and beneficial | Mixed read/group-commit curves, flush p99, CPU/byte, actual RSS, thermal/near-full behavior |
| SATA/SAS SSD | Measure a smaller concurrency knee; avoid saturation that inflates tail latency; distinguish first allocation from overwrite | Limit host write amplification; reserve cleaning space; compare preallocation/prewriting rather than assuming one | Sustained, fresh/overwrite and garbage-collection-state measurements |
| Conventional HDD | Favor long sequential appends and bounded sequential background extents; coordinate random reads with commits; coalesce WAL/index I/O | Reduce repeated seeks between data and index regions; media-aware victim selection/scrub ordering | Seek/transfer break-even for range reads, foreground p99 under cleaning, multi-hour steady state |
| Host-managed SMR/ZNS | Zone-aware append/write-pointer discipline; actual capacity and open/active-zone limits | Reset only after durable relocation and all readers/references are fenced; place mutable metadata on suitable zones/backend | Zoned-device emulator and real hardware tests, interrupted append/reset/recovery |
| USB/removable, virtual, composite, network | Conservative verified flush/alignment fallback; account remote RTT/shared-resource interference; expose uncertain identity | Avoid claiming independent failure domains from logical volumes; handle disappearance and backend changes | Correctness under disconnect/cache/server failure plus real path measurements |

These are hypotheses to measure, not unconditional tuning constants. A laptop needs the smallest resource population that satisfies its workload; a server NVMe may justify many outstanding I/Os. High peak throughput at enormous QD is not automatically an efficient profile.

### 6.4 Zoned mode is detected but not implemented by the volume protocol

A fixed 256 MiB segment is not a zone API. The BlockFile trait has no zone report, capacity, write-pointer, append, reset or open/active-zone management. Alternating superblocks, circular index rewrites and ordinary segment reuse violate sequential-zone constraints on a host-managed backend.

Immediately reject unsupported host-managed paths or implement a separate zoned backend/layout with a proven metadata placement and crash protocol. Actual zone capacity can differ from zone size; active/open limits matter. Reset is a state transition with live-reference implications, not a generic discard hint. Linux documents sequential-write and reset behavior in its [zonefs documentation](https://docs.kernel.org/filesystems/zonefs.html).

A real implementation needs fault injection for out-of-order append, capacity exhaustion, partial reset and lost write-pointer state. Treat “append-oriented” and “works on ZNS/SMR” as separate claims.

### 6.5 Optimize flush cost without weakening acknowledgement

Retain full platform persistence semantics and parent-directory durability where creation/rename publication requires it. macOS full-flush behavior was checked against Rust's implementation; this audit did not find a missing F_FULLFSYNC fallback defect. Windows directory/volume persistence still needs real target validation.

A write-cache field or PLP label does not prove that page-cache writes, filesystem metadata or every controller layer are durable. Skipping a flush requires a backend-specific proven contract, not an identity heuristic. If data and index/log move to different devices, persist every required device and publish their dependency order correctly.

Derive batching from measured flush latency, throughput and foreground SLO. Account small-object latency and first-write cost. Prewriting a whole device can trade latency for long startup, extra bytes and endurance; compute the break-even using actual allocation behavior rather than enabling it universally.

### 6.6 Acceptance evidence for adaptive storage

For each supported backend, record identity, firmware/driver/filesystem, actual caching mode, alignment, capacity, profile version and calibration conditions. Exercise fresh, warm, steady-state and near-full states with mixed foreground and background work. Measure throughput, p50/p95/p99, CPU, memory, physical read/write amplification and flush distributions.

The correctness matrix must also include power-loss simulation, failed/short I/O, corrupt/stale headers, reboot/reopen, directory publication and device disappearance. Measurements on the developer's Apple machine do not certify Linux HDD, Windows SSD or a remote NVMe backend.

### 7.2 Improve object layout according to object size and access pattern

Small objects pay encryption/key metadata plus multiple chunk writes and Block/File/Name transactions. The current 8 MiB chunk choice is derived from Tectonic's large-block workload; it is not a measured optimum for tiny agent artifacts on a laptop.

Measure object-size/access distributions and compare replicated append/packing for small objects with EC for larger sealed blocks. Re-encoding cold data needs an atomic layout-generation transition, ownership-safe retirement and reader fencing. Packing must not accidentally introduce the same unsupported shared-ownership problem as B02. Preserve independent object encryption and deletion/retention semantics.

For range GET, open only the required authenticated segments and read healthy systematic data chunks directly. Reconstruct only on verified failure; budget hedged reads and cancel losers without unbounded repair traffic. Use block/chunk/segment checksums for their respective boundaries, then verify AEAD before returning plaintext. Do not read or decode an entire healthy object merely because the EC API returns owned vectors.

### 7.3 Copy and composition need a deliberate ownership policy

The metadata design explicitly forbids sharing source blocks for CopyObject without owner rows. Today a safe copy must read/reseal/recopy under fresh file/block identities. Missing zero-copy CopyObject is therefore not an existing bug.

If zero-copy, reflinks or deduplicated object composition are desired, first design authoritative multi-owner references, fenced adoption/release, retention interaction and crash-safe cleanup. A physical extent being reachable does not mean a losing operation owns it. The cost and lifecycle of that reference authority belong in the design and benchmarks.

### 7.4 Listing and hot-key scale require precise contracts

Splits help hot prefixes containing many keys. They do not distribute writes to one hot key across several independent linearizable owners. Identify that constraint in capacity planning and use bounded caching/read confirmation or measured per-key admission where needed.

Large listing must stream bounded pages across ordered ranges. Continuation tokens should carry stable logical position, be bounded/opaque and protected against tampering where they encode trusted state. Range/cell generation changes must force correct rerouting. Specify concurrent-mutation pagination behavior rather than accidentally promising a global immutable snapshot for every sequence of list calls.

## 8. Laptop → regional cluster → global fleet

### 8.1 Define global consistency and disaster semantics before building the geography

“Meta scale” is not a consistency contract. The current region/cell design needs explicit answers for cross-region writes, reads and failover. Choose a product model and expose its tradeoffs:

| Model to evaluate | Consequence | Required mechanism |
|---|---|---|
| Regional home for each bucket/range, asynchronous geographic replica | Local normal writes; geographic failover may lose acknowledged updates up to the stated RPO | Durable replication cursor, lag visibility, failover fencing, retention/deletion replication and a stated conflict policy |
| Regional home with synchronous remote durability | Acknowledgement pays required WAN persistence latency; regional disaster recovery can target zero loss only if metadata/data/key publication agree | Remote durable barrier, authoritative ownership/failover epoch, recovery of the same committed graph |
| Active writes from multiple regions with one global ordering authority | Strong semantics require communication with that authority/quorum; partitions limit availability | A deliberate global protocol/placement decision, not an accidental extension of today's independent-cell assumptions |

These are design options, not implemented modes. Define per-operation consistency, RPO/RTO, partition behavior and authority transfer. Strong globally ordered writes cannot promise local latency and successful writes on every side of a partition simultaneously.

Keep ordinary cell-local consensus bounded. Regions can provide many independent strong owners; a geo feature can add explicit replication/ownership semantics without making every metadata range a planet-spanning quorum.

### 8.2 State capacity limits in the units that actually grow

The architecture names the right cell bounds but does not yet provide validated values. Record measured limits for ranges, placement entries, chunk fragments, sessions/replies, bytes of caches, repair queue and placement solve time.

Useful accounting equations are:

    Block placement rows ≈ logical data / logical block size × stored chunk width
    Node working memory = range/core/engine state + indexes + queued/executing I/O
                          + retained replies + snapshots + network + coding buffers
    Full-map distribution bandwidth ≈ routers × map bytes / refresh interval
    Recovery time ≥ required bytes / available sustained recovery bandwidth

The root map's periodic full distribution makes request rate less dependent on cache misses, but it does not make map size or router fanout free. [architecture §4](../design/architecture.md#4-the-cell-map) needs a measured map-size/receiver ceiling and a dissemination strategy within that ceiling. Evaluate hierarchy, aggregation, bounded deltas or regional fanout if the full-map budget is exceeded; preserve persisted last-good routing and epoch fencing.

Use explicit hardware/resource ceilings to trigger split, cell addition, admission or tenant isolation before emergency saturation. Scale tests must include metadata/index memory for small objects, not only large sequential object throughput.

### 8.3 Close the durability loop with measured placement and repair

The implemented durability model already includes failure domains, burst losses and serial repair; claiming it assumes only independent disks would be wrong. Its rates are inputs, however, and a chosen code does not create a working placement or repair service.

Measure detection plus rebuild under real contention. Reserve capacity and network/device bandwidth to recover the largest supported failure domain while another failure remains plausible. Prioritize by remaining redundancy, authenticate/verify every source, install new placements by generation, and retire old chunks only after readers and metadata publication are safe.

Use the Block reverse index for bounded per-volume discovery, persist/restart repair tasks, and reject impossible topology rather than placing several logical chunks on one physical failure domain. Multiple logical volumes or NVMe namespaces on one device are not independent copies.

The default 10^-11 target is **per block**. The design correctly gives the union bound for objects: an object of one million blocks has an upper bound of 10^-5 under that target. That is an upper bound, not a prediction of its actual loss rate. If the product promises S3-like eleven-nines object durability for very large objects, derive a corresponding block/size policy or qualify the service class. Include loss of metadata or encryption keys, correlated events and software-driven deletion in the operational story; parity cannot repair a missing authoritative name/key.

### 8.4 Fence repair/rebalance against reclamation

The Name reclaimer reads chunk places, deletes chunks, then issues Block Delete. It does not first establish the Block release fence used by the orphan sweep. A future concurrent block::Move can install a new chunk between the location read and deletion, after which removing Block metadata forgets that newly placed chunk.

This is a **production integration obligation**: repair/rebalancing and per-volume reconciliation are still planned. Establish a release/move fence before reading places for destruction, or prove an equivalent generation-based protocol; then reconcile abandoned writes promptly. Test move-versus-delete in both orders and with crashes at every step. Do not solve it with an arbitrary sleep.

### 8.5 Make cross-cell migration a fault-tested protocol

The source's epoch/tombstone direction is appropriate. The complete protocol must cover objects, versions, upload parts, bucket settings, ownership/dispositions, encryption keys and in-flight cleanup—not just copy a Name table and point the router elsewhere.

Test every durable boundary: partial copy, catch-up, source write fence, destination publication, map CAS, stale router retry, old-owner tombstone and final source reclamation. Include source/destination loss, duplicate movers, failed final flush, old gateway commands and retries after cutover. Old-epoch mutations must be refused after ownership changes.

Destination readiness needs a verifiable inventory/checkpoint and replay frontier. A switch without all required File/Block/chunk/key state creates an authoritative route to incomplete data. Build one tested migration path before scaling to a situation that needs migration to escape a full cell.

### 8.6 Bound storage debt, cleanup and tenant interference

A grace period consumes real capacity. Size headroom for the maximum admitted ingestion/deletion debt, read grace and worst supported repair, alongside cleaner runway. Bound release/sweep/repair queues in bytes and work, and expose their age. Do not let an inactive tenant leave unlimited multipart or abandoned-write debt.

Give foreground requests, consensus control traffic, snapshot/repair and cleanup separate fair shares under one device/node budget. A background deadline should not force unbounded foreground latency, and a tenant with 10,000-part completions should not starve another range's reads or elections. Overload must be visible as a typed, retryable response rather than process OOM or a stranded Ready.

### 8.7 Ship upgrade and recovery protocols, not just healthy-path scaling

Persist and negotiate supported wire/disk/engine versions. Stage activation of new semantics such as fast track or ownership formats across mixed-version members. Define rollback boundaries, unknown-field/version refusal and interrupted migration handling. A bad shared-log upgrade can affect many ranges on one node; rollout and replica placement should limit that overlap.

Backups/disaster recovery need a coherent metadata/data/key recovery point, restoration tooling and regular drills. Replication propagates an erroneous reclaim decision just as efficiently as a correct one. Restoring bytes without names, disposition state or wrapping keys is incomplete recovery.

### 8.8 Observable operating limits and acceptance milestones

Propagate existing disk histograms, read refusal/high-water data, scrub findings and writer failure state into service telemetry. Add queue/held/executing bytes, apply/flush/ReadIndex latency, per-range leader churn, snapshot lag, repair redundancy/debt, stale-route/migration epochs and object checksum/AEAD failures. Track causes and denied work, not only success throughput.

| Milestone | Evidence required before calling it achieved |
|---|---|
| Laptop serving | Real S3 PUT/GET/HEAD/list/delete/multipart path; one process with the production engine; bounded idle/busy RSS; restart and disk-full safety; unsupported redundancy reported accurately |
| Multi-disk single node | Proven device identity/capacity; physical-domain-aware placement; degraded reads/repair; disk removal and replacement; HDD/SSD/NVMe profile measurements |
| Regional cluster | Real authenticated transport, 3/5-voter histories, topology-aware metadata/data placement, node/rack/zone failures, slow receivers, learner/snapshot pressure and near-full sustained load |
| Multi-cell region | Root map recovery, stale-route fencing, live migration, full-cell relief and one-cell failure/load surge isolated from peers |
| Global fleet | Chosen geo consistency/RPO/RTO contract; region-loss/failover fencing; measured full-map/placement/repair limits; safe staged upgrades and recovery drills |
| Meta-scale claim | Repeatable tests at the largest supported cell/control-plane cardinalities and fleet distribution model, with published resource/SLO limits and failure scenarios—not an extrapolation from one SSD benchmark |

## 9. Security, code structure, and operational correctness

### Security boundaries to retain and finish

The code has useful existing defenses: constant-time signature comparison, strict/bounded parsers, JSON depth bounds, rejected XML DTDs, explicit unsupported encryption modes, OS-generated data keys, wrapped per-file keys, zeroized customer/data-key storage, authenticated segment identity/lastness and guarded crypto/EC calls. These are concrete implementation choices, not an end-to-end service security certification.

Finish the boundaries that the future serving/distributed path will create:

- Derive policy context, owner identity, SSE-C authorization and bypass privileges from authenticated server facts, never caller-supplied internal command fields.
- Apply HTTP/header/body and decoded-byte admission before allocation; resolve ambiguous duplicate headers/query parameters consistently across routing, signing, policy and body handling. Test request smuggling at the selected server/proxy boundary.
- Do not publish Name state until body hash, signed chunks, required trailer checksum and length validate. Uncommitted chunk writes must be recoverably reclaimed without violating B01/B02.
- Give distributed nodes authenticated roles and credentials; CRC protects against accidental corruption, not unauthorized mutation. Bound replay/failed authentication work.
- Make root-key generation an unambiguous shared authority across gateways/cells. A local “generation 1” label is insufficient if two nodes mean different keys. Persist/backup the relevant key authority, retain old unwrap capability through rewrap/migration, and test node/region loss during rotation.
- Consider zeroizing SigV4 secret Strings, signing-key intermediates and Chain's key storage; Chain currently hides keys in Debug, but visibility protection alone does not wipe retained copies.
- Separate a stateful sealing API from opening, or document/enforce one-key/one-file/monotonic segment use at the gateway seam. The current gateway increments segment indices correctly; the low-level Segments::seal(&self, index, ...) permits caller-induced nonce reuse. This is an API hardening opportunity, not a reproduced confidentiality breach.
- Preserve patched RNG fallback/fallible crypto behavior on every target; catch_unwind cannot contain a C abort or Rust allocation abort. Continue auditing those distinct failure modes rather than equating an unwind guard with universal containment.

Dependency revisions and local crypto patch provenance are recorded, and the vendor suites passed in this audit. Keep checksums/provenance, minimal features, fresh advisory review, reproducible builds and targeted patch regression tests on all supported platforms. No specific dependency vulnerability was found by the cached advisory scan.

### Deepen the boundaries implicated by actual defects

The pure request/answer state machines and OS-backed BlockFile seam make the code testable. Preserve those seams. The most useful design improvements are tied to discovered failures:

1. **Ownership authority:** give prepared, adopted, released and reclaimed states explicit persistent meaning. Make reclamation request authorization from that authority instead of inferring ownership from a missing mark or an extent. A possible design is a Name-range ownership/disposition ledger tied to completion and a fenced token identifying the winning parent; it still needs a crash/retention proof and bounded lifecycle.
2. **Resource ownership:** reserve work budgets through queued → deferred → executing → completed/cancelled. Centralize that lifetime rule so dequeue cannot silently free a live allocation's accounting.
3. **Persistence staging:** expose immediately-sendable versus durability-dependent messages and retain pending Ready explicitly. Keep failure/backpressure state representable rather than dropping a necessary object through ?.
4. **Backend capabilities:** validate and bind path identity, actual capacity, alignment, caching and durability constraints at open/format. Put generic application code behind a proven backend contract rather than scattered device-name decisions.
5. **Contract maintenance:** derive or cross-check protocol limits and wire budgets, and connect specification claims to named mutation/regression tests. Large files containing extensive tests are not, by themselves, evidence that modules need cosmetic splitting.

Avoid broad refactors before closing the proven failure schedules. New abstractions should make an invariant harder to violate, reduce duplicated decisions, or provide a meaningful test/measurement seam.

## 11. Comparative audit of Slates and Focal: implemented optimizations and adoption boundaries

### 11.1 The comparison is between different products and concrete source revisions

The continuation examined Slates at **8ab25deb7c31bfca77a33cc681ce120bac76e7d1**, including its working changes to fleet diagnostics, gap ledger and audit, and Focal at **801ba65b35ea69508725e8e73407b3e6b7c3b782**, including changing node control/fleet/directory/network feedback work. Slates' transport and Raft core and Focal's core/consensus/log/wire implementations were committed at that inspection cut. WIP owner feedback is not a released guarantee. The audit read their implementations, design/build ledgers, hostile-path tests, allocation records and measured/rejected experiments. It did not treat sibling audit conclusions as proof without tracing code.

Slates is a RAM-only copy-on-write filesystem. Its regional council and root Raft groups handle configuration/failure-path coordination; ordinary data writes use its fenced-register protocol. Focal is a proof-of-work ledger with independent session logs and committed placement/control. Mantle commits Name/File/Block metadata continuously and persists object chunks to heterogeneous media. Consequently a fast configuration benchmark, an in-memory register acknowledgement and an object-store durable acknowledgement are different contracts.

Mantle pins focal-raft at **1395e223c065e85158ec1611fdc72073d28fd8a0** in [range/Cargo.toml](../../crates/range/Cargo.toml#L13). The later focal-raft production delta is small: owner-supplied election patience, rather than a new consensus/transport architecture. Classic Append pipelining, fast proposals, priority, joint configuration, learners, transfer and ReadIndex already exist at the pin. Mantle imports the core; Focal's durable shell, QUIC, authentication, memory budgets and fleet scheduler do not arrive transitively. A dependency upgrade alone fixes none of the missing integration contracts below. Focal itself describes global capacity as an [unmeasured envelope](../../../focal/docs/qualification/capacity-envelope.md#L76).

### 11.3 Focal's useful persistence design, and the differences that must survive a port

[Focal RawNode](../../../focal/crates/focal-raft/src/node.rs#L194) owns one outstanding Ready and refuses mutation until it advances. [Focal persistence](../../../focal/crates/focal-consensus/src/persistence.rs#L93) reserves completion staging before acquiring Ready, retains prepared storage and a receipt, and returns to its owner without waiting for disk. After the receipt, it publishes the durable view and releases dependent events. Its [persistence tests](../../../focal/crates/focal-consensus/src/persistence_tests.rs#L138) stage twelve groups behind a controlled barrier and assert one covering initial flush, blocked authority before that fence and correct later event publication. This is substantive cross-group batching evidence.

Port that shape to Mantle: each range actor owns its Ready, ordered split parts, generation and disk ticket. A nonblocking submission either obtains room or retains the exact part for a capacity notification. A completion wakes the correct actor; it must not require scanning every range. The actor emits only durability-eligible outputs, submits the next part and yields after a byte/time budget. Core inputs arriving meanwhile remain in bounded owner queues. Fatal flush/write errors fence the whole affected durability domain. Snapshot and Engine completion must use the same ownership discipline.

Focal's shell conservatively holds even leader-sendable messages until persistence. Mantle should preserve its core's safe leader-send overlap as a separate improvement. Likewise, Focal queues an additional LightReady commit fence before releasing complete output; Mantle deliberately permits some committed apply without immediately persisting that LightReady commit and repairs the WAL commit on restart from durable Engine state. See [replica design](../design/replica.md#L121) and [commit recovery](../../crates/range/src/replica.rs#L745). These are different recovery models. Copying or deleting fences without proving which durable state covers a client answer would introduce a correctness defect.

The ticket contract must state that cancellation removes the caller's interest, not an already admitted write. An ambiguous timeout cannot be called failure-with-no-effect, and queue admission is never durable success. Late completion after actor/range/device replacement needs a generation check and cleanup ownership. A per-range two-request queue limit is useful protection against a hot range, but does not provide service fairness or aggregate completion capacity among thousands of ranges.

### 11.4 Slates' pipelining is a relevant measured mechanism, not a fleet throughput number

[Slates replicate_to](../../../slates/crates/cluster/src/raft.rs#L2152) distinguishes a probing follower from a confirmed one, sends bounded batches ahead while a window permits it, backs up using conflict hints, and falls back to snapshots below the retained boundary. Its [timing law](../../../slates/crates/cluster/src/timing.rs#L206) derives ahead capacity from approximately `batch_bytes × ceil(2 × measured_tail_RTT / heartbeat_period)`: a lost batch takes a refusal round and a repair round. It also indexes configuration entries and computes the majority match position instead of scanning every backlog index.

Recorded five-region simulation, with 21-byte entries and a 4,367-byte batch, changed a 2,000-proposal/s workload from **7,319 ms median / 14,378 ms p99** without an ahead window to **172 / 222 ms** with one batch. At 1,000/s it reduced sent bytes by about 14%; at 20/500/s it changed nothing. A backlog optimization reduced the recorded leader proposal cost at 5,000 entries from 20 ms to 96 ns. These are [Slates' recorded experiments](../../../slates/docs/wip/BENCHMARKS.md#L860), not measurements of durable Mantle entries. Their remaining 4,000/s overload also shows that a window does not eliminate the next bottleneck.

Mantle must bound inflight **bytes**, retained unstable/durable entries and receiver work together; message count times maximum append size can be very large. Derive initial windows from durable-ack path latency and sustainable sink rate, then adapt within node/device budgets. Measure `min(leader encoding/CPU, WAL durability, follower durable-ack rate, network/window, engine apply)` rather than assuming network RTT is the only limiter. Confirmed progress must not move backward on a late reply; reject stale range/term/incarnation callbacks. Preserve bounded conflict-hint repair and snapshot feedback while local Ready is outstanding.

### 11.5 Fast track needs an application and persistence proof for the chosen dialect

Mantle already persists proposal rows and restores them: [log Proposal](../../crates/log/src/lib.rs#L77), [LogStore initial_state](../../crates/range/src/store.rs#L80), [Ready conversion](../../crates/range/src/replica.rs#L817). Claiming those hooks are absent would be wrong. What remains absent is an enabled durable group mode, public fast proposer/displaced-completion handling and object-store qualification.

Focal's fast quorum is `ceil(3M/4)`: all three voters for a three-voter group, four for five voters. Approvals must be durable before a vote says it holds a proposal. Election recovery, term restamping, proposal replacement and committed-payload comparison form one algorithm. Its [fast owner requirements](../../../focal/docs/archictecutre/27-consensus-roadmap-and-slates-port.md#L254) prohibit deriving application authority from entry term, require deterministic evaluation and require displaced requests to be retried/accounted. Durable group identity and checkpoint/reopen compatibility are essential.

Slates uses a different generalized log/window algorithm. It retains accepted slots until a **classic** commit covers them and separates its leader's fast application frontier from the commit index followers retain. Its prefix model found chosen-value loss after dropping slots at sync/election, and log-matching failures after pruning under a fast commit; the [corrected design](../../../slates/docs/wip/research/consensus-enhancements.md#L260) keeps those counterexamples. **Do not transplant Slates' pruning rule into Focal in isolation**: Focal releases proposals after replacement by leader-log entries and depends on its own recovery/restamping rules. Reuse the adversarial schedules and proof obligations; retain the selected algorithm's complete invariants.

The measured crossover argues against blanket enablement. Slates recorded a far proposer improving **435→275 ms** median without loss, but a leader-local proposer worsening **156→201 ms**, and 10% loss worsening every region and reducing completed requests. Both actual Slates groups propose from their leaders and therefore keep classic. Focal's simulation also has counterexamples to universal improvement: LAN/three voters/5% loss mean **17.9 vs 14.6 ms**, and regional/three voters/1% loss p99 **411.2 vs 366.1 ms**, despite its median gate passing. See [Slates crossover](../../../slates/docs/wip/BENCHMARKS.md#L832) and [Focal comparison](../../../focal/docs/archictecutre/27-consensus-roadmap-and-slates-port.md#L230).

Mantle's test must account for **every admitted request** as committed once, explicitly displaced/retryable, or unknown pending recovery. A later successful request alone does not prove an earlier hole was filled. Include multiple indices/terms, holes, losing proposals, persistence rejection, snapshot/compaction, removed voters, Name ownership/session rows, split barriers and leader loss after an acknowledgement. Real flush latency, concurrent load, CPU and wire bytes must enter the comparison. Small exhaustive models and virtual milliseconds are evidence within their scopes, not a storage/global proof.

### 11.6 Multi-Raft, MLRaft and parallel application solve different problems

Mantle needs many independent Raft ranges with shared runtime/device ownership. Slates' MLRaft instead distributes one logical group's commands among logs and inserts barriers for global commands. Its recorded five-log result worsened steady keyed latency **174→302 ms**, global latency **199→839 ms**, and messages roughly fivefold; failure of a non-designated log could stall all keyed streams for **3.7–6.3 seconds** behind barriers. [Both groups retain one log](../../../slates/docs/wip/BENCHMARKS.md#L991).

Do not add that barrier model to Name/File/Block operations as an automatic scale enhancement. Existing bottom-up handover and the Name linearization point need their own authority/cleanup proof; cross-layer log barriers are not a substitute. Prefer independent range placement/splitting and bounded cross-range workflows. A single hot key remains serialized by its semantics; adding unrelated shards cannot accelerate conflicting mutations on that key indefinitely.

Focal's parallel materializer stages **committed outcome records**, validates recorded dependencies, discards stale speculative suffixes and publishes in order. Its [recorded improvement](../../../focal/docs/archictecutre/25-parallel-materialization-and-ranges.md#L84) was 910→620 µs for eight independent records and 928→913 µs for dependent ones. Mantle logs commands evaluated against mutable metadata: session answers, clocks, bucket settings, upload parts, marks/releases and range descriptors create dependencies. Cross-range parallelism and removal of full scans are earlier wins. Speculative in-range apply needs complete dependency tracking, an ordered atomic Engine prefix and differential histories against serial execution.

### 11.7 Elections, ReadIndex, learners and shutdown under load

Slates derives election base/span from measured path tails/spread, uses quorum RTT as leader preference, and keeps preference outside vote safety. Its learner catch-up, minimum election lease lapse, independent jitter and transfer fixes have source-backed simulations plus real process/KIND measurements. The [timing implementation](../../../slates/crates/cluster/src/timing.rs#L170) and [priority evidence](../../../slates/docs/wip/BENCHMARKS.md#L914) are useful references. They also record failed variants and tied-successor split votes; preference is not a guarantee of immediate convergence.

For Mantle, measure append **durable-ack** and owner scheduling/flush delay alongside raw network RTT. A central node with slow HDD/overloaded coding may be a poor leader. Use hysteresis and a bounded transfer rate per node/cell; stagger group elections and drain handoffs to prevent correlated storms. Do not stretch every timer indefinitely under overload. Focal's newer patience accounts for observed owner/path stalls, but unknown paths and startup still require a progress policy. A timeout diagnoses liveness; it never changes quorum or durable voting rules.

Keep learner catch-up before joint promotion, and require the final voter set to learn the committed configuration before declaring replacement complete, as Mantle already does. Bound simultaneous catch-up bytes and repair/snapshot pressure across failure domains. Graceful shutdown should wait for a successor's demonstrated authority where available, not merely the old leader stepping down; otherwise a rolling update can still leave no leader.

ReadIndex must remain correlated to the correct range generation and applied prefix. Bound read contexts, caller waiters and response bytes; cancel them safely; batch safe barriers when a single confirmed prefix covers several reads. Follower reads are useful but still pay quorum confirmation and wait for local apply. Clock leases require an explicit deployment clock bound; neither transport RTT nor a timeout alone establishes it.

### 11.8 QUIC stack comparison and immediate adoption blockers

Slates implements packet protection, multiple streams/exchanges, absolute stream/connection credits, credited stream concurrency, ACK ranges/ACK-of-ACK, PTO/time/packet loss, pacing, Copa, DPLPMTUD and adaptive reordering. Actual council/root traffic currently uses priority streams on record sessions ([fleet.rs](../../../slates/crates/server/src/fleet.rs#L4594)); the older draft's datagram-consensus text is not a reliable description of current wiring. Several module headers likewise still call built MTU/timing/congestion work owed. Follow code and build ledger.

Focal uses Quinn's standard QUIC transport plus private application ALPN/envelopes, mutual TLS, per-stream authorization, lane admission, route revision fencing, reconnect and delivery feedback. Its [transport](../../../focal/crates/focal-wire/src/transport.rs#L195) disables early data and uses custom Copa. Slates' private stream-ID/handshake/frame dialect is not Quinn-compatible. Neither internal protocol is the public S3 HTTP interface; HTTP/3, if offered, requires its own standard HTTP/QUIC integration ([RFC 9114](https://www.rfc-editor.org/rfc/rfc9114.html)).

**Slates whole-exchange retention.** [open_exchange](../../../slates/crates/transport/src/connection.rs#L449) copies the complete request through [StreamSender::write](../../../slates/crates/transport/src/stream.rs#L41), while [Endpoint::drain](../../../slates/crates/transport/src/endpoint.rs#L1350) accumulates complete request/reply vectors and advances consumed flow credit. A fresh local probe with an **8 KiB receive ceiling accepted a 32 MiB request**, made four allocations requesting **33,555,376 bytes**, and caused **2,053 minor/0 major faults** during open on this macOS host with 16 KiB pages. The source request was constructed before measurement. These are allocation requests and local fault deltas, not RSS or throughput. Flow credit bounds wire-ahead bytes, not this retained application copy. Bulk objects/snapshots therefore need a streaming source/sink API and aggregate application-buffer admission before adoption.

**Slates congestion accounting.** [tracked_bytes](../../../slates/crates/transport/src/conn.rs#L217) counts only Stream payload; [record_sent](../../../slates/crates/transport/src/connection.rs#L794) charges those bytes to inflight and the pacer. The same probe's one-byte request produced a **23-byte encoded frame**, plus packet header/tag up to 29 bytes, while its charged payload was one byte. Packet number length can make actual overhead slightly smaller; the omission remains. A control-only packet can have zero stream charge. Maintain separate useful/application bytes and congestion-accounted serialized packet bytes, with correct ACK-only exemptions and probe behavior. This matters most for tiny control messages, cancellations, lossy retransmissions and thin links; the current bulk grids do not establish correct accounting there. [RFC 9002 §B.2](https://www.rfc-editor.org/rfc/rfc9002.html#section-b.2) counts the QUIC header/tag in bytes in flight.

This omission is not shared by Focal's inspected dependency: resolved **quinn-proto 0.11.18** constructs the packet with its header and authentication tag, charges the finished packet size to pacing/inflight, and excludes PMTU probe losses from the ordinary congestion response. The inspected paths are packet construction/finish and path sent-byte accounting. IP/UDP headers remain outside QUIC's specified bytes-in-flight measure. Focal passes Quinn's acknowledged-byte count through to its [Copa controller](../../../focal/crates/focal-wire/src/congestion.rs#L485); transport comparison must retain these accounting differences.

**Focal credit multiplication.** Current consensus-derived limits allow 142 application streams plus two reserved streams. [quic_transport](../../../focal/crates/focal-wire/src/transport.rs#L197) permits roughly **144 MiB connection receive/send windows**; over 128 outbound connections that is **18 GiB** before inbound/application buffers. These are possible credit ceilings, not eager allocation or measured RSS. Quinn's buffers are outside Focal MemoryBudget. Raising concurrency fixed an old two-exchange choke but enlarged the unaccounted envelope. Mantle must derive aggregate credits from available node/device/tenant memory and use small independent control allowances; do not copy these constants.

**Focal allocating receive before handler admission.** [frame helpers](../../../focal/crates/focal-wire/src/frame.rs#L59) allocate and zero complete envelopes, then decode owned fields; production [request handling](../../../focal/crates/focal-wire/src/transport.rs#L509) admits the handler afterward. A permitted 10 MiB slow frame can therefore touch its full application allocation before payload arrival. Caller-buffer helpers exist; the selected path matters. Reserve raw-frame and decoder capacity before reading, then carry that reservation through worker/output/cancellation ownership.

**Restart/security authority.** Authenticate node identity separately from range/tenant authority; bind sender, group, descriptor/placement epoch and operation identity. Disable replayable early mutation unless an explicit durable anti-replay protocol covers it. Slates' pure control [Enrollment::sealer](../../../slates/crates/transport/src/enrollment.rs#L71) constructs a [counter-zero Sealer](../../../slates/crates/transport/src/seal.rs#L137); constructing another under unchanged key/channel reuses the nonce namespace. Its secret-distribution half is explicitly owed. Mantle must establish a durable counter reservation or a fresh authenticated key/incarnation before first send after restart, with bounded key overlap/revocation. This is an adoption obligation, not a claim that the current Slates session TLS path has reused a nonce.

## 12. Allocation, reallocation, copies and page faults

### 12.1 Fix ownership and asymptotic work before choosing a faster allocator

A different allocator cannot remove a required full-payload clone, a retained parent buffer, repeated session serialization, growing manifest work or a queue outside admission. The largest expected gains are fewer materializations, bounded reusable working slots and eliminating work that scales with history/backlog. Measure those first; then compare allocators against fragmentation, CPU, RSS, platform support and pressure on the actual mixed workload. No allocator swap is justified by a microbenchmark alone.

Count **allocation and reallocation calls, requested/retained capacity, copied bytes, touched pages and peak live ownership** separately. A geometric Vec reserve can reduce reallocations but retain excessive capacity; reserve-exact on each append can copy a growing log repeatedly. A small Bytes slice can keep an entire large parent alive. Charge shared backing allocations once through their last owner, and charge containers/temporary encodings separately. Pooling free buffers is not admission for active borrowed buffers.

### 12.2 Concrete allocation/copy map

| Path | Source-confirmed cost | Change to evaluate, preserving safety |
|---|---|---|
| Gateway input and sealing | [take](../../crates/gateway/src/put.rs#L419) copies into a segment; [seal_segment](../../crates/gateway/src/put.rs#L449) appends to a block; mem::take transfers filling capacity away | Owned block/segment slots with explicit tag space; seal into final positions or retain bounded vectored segments; recycle after the last user finishes |
| Copies versus EC | Copies shares one Bytes backing allocation, and AEAD already encrypts in place; EC copies originals, creates parity/workspace and later copies reconstructed outputs | Credit existing efficient paths. Reuse admitted EC workspaces; borrow systematic shards and reconstruct only needed outputs where supported; measure source+parity+scratch peak |
| Chunk ingestion/formatting | [Volume::write](../../crates/chunk/src/volume.rs#L349) copies borrowed input; [writer](../../crates/chunk/src/writer.rs#L1057) builds aligned regions; [record encode](../../crates/chunk/src/record.rs#L152) separately builds headers/checksum tables | Accept admitted immutable owned payloads; encode headers/table into final buffers; compare bounded gather/vectored IO with contiguous copies using actual alignment/flush requirements |
| Small/range GET | Output, aligned read span, EC copies and decrypted bytes can coexist; P01 reads unnecessary prefixes | Admission before output allocation; caller-owned segment outputs, direct systematic reads, targeted rebuild, verified in-place decrypt and bounded response streaming |
| Ready/commands/log views | [propose](../../crates/range/src/replica.rs#L393) encodes before checking its byte limit; [update_of](../../crates/range/src/replica.rs#L785) encodes each entry into Vec and then a copied Arc allocation; part retries clone containers | Admit encoded size before encoding, build one immutable backing allocation, transfer/recover Update ownership on refusal, and retain the Ready through all ordered receipts |
| Shared-log frame | [writer](../../crates/log/src/writer.rs#L195) builds Payload; [format](../../crates/log/src/format.rs#L98) copies it into Frame; [write backing](../../crates/log/src/writer.rs#L439) copies Frame into fresh zeroed aligned storage | Encode into one admitted reusable aligned frame, preserving padding, CRC, segment ordering, full flush and publication; reuse sizing/descriptor scratch without payload materialization |
| Sessions/manifests/directories | P02–P05 serialize/scan or allocate collections repeatedly; dense block indices use tree nodes | Separate session answer rows with byte retention, bounded batch directory updates, dense slots where order/IDs permit, streaming extent/list plans and indexed expiry work |
| Snapshot/install | Engine image, encoded bytes, per-peer copies and decoded rows coexist | Consistent streamed range view, verified chunks, bounded install staging and atomic durable prefix publication; reserve catch-up traffic separately |
| Internal peer frames | Slates whole-exchange vectors and Focal raw-frame/decode buffers exceed transport-only accounting | Streaming body APIs, borrowed fixed-header parse, one admitted owned payload per stage and capacity tokens across handoffs |

Avoid calling every Arc/Bytes clone a payload copy. Conversely, a cheap reference clone can keep a very expensive allocation alive. A fallible reserve is useful only if the sum of permitted concurrent reservations fits the actual process/cgroup envelope.

At f422d1e, a Ready carrying E payload-scale bytes and a frame carrying L of those bytes can retain roughly **2E + 3L** across Ready data, encoded Arc data, Payload, Frame and aligned backing, before unstable-log owners, messages, container capacities and metadata. For E≈L these owners approach **five payload-sized copies**. This is a source-derived ownership model, not measured RSS; encoding overhead and unrelated owners are omitted. Vec→Arc creates a new allocation and copies items ([Rust implementation](https://doc.rust-lang.org/src/alloc/sync.rs.html)); subsequent Arc clones share it. Removing the Payload→Frame→aligned passes targets two full-frame copies and repeated zeroed allocation directly.

[Sizing/encoding helpers](../../crates/log/src/writer.rs#L1000) also create temporary entry-descriptor vectors, and each accepted submission creates its own one-slot reply channel. Iterate borrowed descriptors directly, reuse bounded writer scratch and evaluate generation-tagged completion slots. An admission refusal must return ownership; cancellation can release caller interest but cannot erase an accepted durability outcome.

Cold [Storage::entries](../../crates/range/src/store.rs#L104) remains synchronous and copies decoded context/data into owned Raft entries. The pinned Focal Storage interface has no entries-fetched callback/GetEntriesContext mechanism that makes this fetch asynchronous. Receipt-driven writes alone therefore do not make a multi-range owner nonblocking: cold reads, snapshot construction/install and apply can still stall it. Use bounded prefetch/cache admission or design and prove a new storage/core interaction; moving arbitrary synchronous work into a pool without ordering and completion bounds is insufficient.

For image size S and d stalled recipients, [snapshot delivery](../../crates/range/src/store.rs#L149) can add d×S cloned message bytes to its retained source image. Building/installing additionally materializes encoded bytes and owned rows. The inline format is explicitly temporary. A pinned immutable checkpoint, bounded transfer chunks and atomic install publication should replace complete per-recipient vectors; one outstanding Ready does not bound these transfer peaks.

### 12.3 Reuse without unlimited retention or unsafe initialization

Use bounded size classes for control frames, authenticated segments, chunks and coding workspaces. Charge live slots and cached capacity independently; enforce per-shard caps that sum to a node cap. Keep generation-tagged handles so late IO/transport callbacks cannot use a recycled slot. Release or shrink oversized idle caches under pressure, using a measured break-even policy rather than shrinking on every request. Bound reserve refill work and make allocation refusal leave the state machine retryable.

[AlignedBuf::zeroed](../../crates/disk/src/buf.rs#L128) reserves alignment slack and initializes backing storage; pooled buffers reuse initialized memory. Prefer that reuse, and zero required padding/newly exposed bytes once. Never checksum, encrypt, send or persist uninitialized storage. Ciphertext buffers, plaintext buffers and key-bearing buffers require distinct reuse/zeroization rules. Faster initialization must not leak prior request contents or weaken authentication.

At the verified default settings, [chunk pools](../../crates/chunk/src/volume.rs#L152) can retain **32 MiB reader + 64 MiB writer = 96 MiB per volume**, or **1.5 GiB across 16 volumes**, before checked-out buffers, caller outputs, queued payloads, log/cache/engine state and filesystem cache. These are maximum warmed free-buffer capacities, not eager startup allocations. Pool limits cover returned free buffers rather than all live buffers. Oversized buffers that cannot be retained can repeatedly allocate/fault after each use. Node-wide pressure and live-byte permits must govern the sum; independently safe local defaults can exceed a laptop's RAM when composed.

Slates offers useful references: [segmented storage](../../../slates/crates/mem/src/segmented.rs#L1) grows without moving existing elements, [slabs](../../../slates/crates/mem/src/slab.rs#L1) reuse generation-tagged slots, and its [no-allocation test](../../../slates/crates/mem/tests/no_alloc.rs#L43) exercises warmed slab/arena cycles with zero system allocations. Both that test and its counter-isolation test passed in this continuation. This proves the tested warmed memory operations, not that Slates networking or Mantle's full PUT is allocation-free. A typed admission bound should determine maximum capacity, rather than preallocating the global worst case for every range/peer.

Focal's [allocation record](../../../focal/docs/qualification/allocations-2026-09-29.md) is also instructive: a Raft harness that delivers messages newest-first and clones them can manufacture reprobes and apparent batching gains. FIFO core attribution still shows meaningful allocation cost. Separate harness, codec, core, transport and application allocations; count bytes and ownership, not only calls. Focal's faster [byte decode](../../../focal/docs/qualification/performance/2026-09-29-macos-arm64.md) preserved format and reduced visitor CPU, but does not eliminate the whole-frame encode/read/decode copies. Mantle already has slice-oriented codecs in several paths; profile its own remaining copies.

### 12.4 Page-fault work belongs in admission and scheduling

Fresh multi-MiB copies touch many pages. At this host's measured **16,384-byte page size**, a 32 MiB new payload spans 2,048 base pages before allocator overhead; the probe observed 2,053 additional minor faults. That is a concrete cost of ownership duplication, not evidence of disk major faults or a universal per-page timing. Record base page size and distinguish minor faults, major faults, compressed/swapped pages, page-cache misses and IO stalls.

Slates' [prefault scheduler](../../../slates/crates/mem/src/prefault.rs#L1) derives pages per idle slice from measured fault cost, yielding between batches; its [Region](../../../slates/crates/mem/src/region.rs#L1) supports mappings/advice/locking. Adopt the bounded scheduling idea for a measured active working population. Prefaulting the maximum theoretical pool lowers some hot-path faults by eagerly raising RSS/startup work; it does not reduce total resources. Do not prefault all possible peer windows or data capacity.

On NUMA servers, align shard ownership, first touch, coding workers, NIC queues and device queues where topology is known. Linux's local policy starts at the allocating CPU's node ([NUMA policy](https://docs.kernel.org/admin-guide/mm/numa_memory_policy.html)); moving a handle later does not relocate its pages. Slates' [NUMA setter](../../../slates/crates/mem/src/region.rs#L140) records a node identity without binding/migrating memory. Measure actual remote-memory bandwidth/cache misses, and cap local reserves globally. Registered/pinned IO buffers consume a separate finite resource and must survive until kernel completion; cancellation of interest cannot release them prematurely. Ordinary portable buffers remain necessary for laptop/unsupported platforms.

Huge-page advice can reduce TLB overhead for suitable large long-lived buffers but can waste memory for sparse structures and introduce allocation/compaction latency. It needs a per-arena measured policy, pressure behavior and ordinary-page correctness. Linux explicitly documents memory/latency tradeoffs in [THP guidance](https://docs.kernel.org/admin-guide/mm/transhuge.html); [madvise](https://man7.org/linux/man-pages/man2/madvise.2.html) population/advice calls are platform-specific and can fail. Prefaulting/locking is a resource choice, not permission to exceed a budget. Protect small control/metadata working sets without indiscriminately pinning bulk bytes.

Buffered IO can retain application buffers plus filesystem cached/dirty pages; direct IO still needs resident aligned user buffers and complete persistence semantics. Measure dirty-writeback throttling, cold restart/page-cache behavior and near-RAM-limit operation. Sequential recovery/scrub can use bounded readahead/advice while avoiding eviction of hot metadata; arbitrary mmap does not eliminate faults or establish persistence. Zero major faults under the admitted steady envelope is a useful goal, but major-fault absence alone does not prove low memory use or absence of compression/writeback stalls.

Mantle currently uses positional file IO. A cold buffered pread's page-cache miss causes device IO in the syscall; it is not itself a user file-mapping major fault. Count file input, cold-read latency and reclaim/writeback alongside [getrusage fault counters](https://man7.org/linux/man-pages/man2/getrusage.2.html). Report whether direct mode actually opened or fell back to buffered mode. Establish cold behavior using a measured working set/disjoint passes and observed IO, without relying on privileged global cache drops.

On constrained Linux hosts, [memory.high](https://docs.kernel.org/admin-guide/cgroup-v2.html) can throttle allocation and force reclaim before memory.max. Track process/cgroup usage and [pressure stalls](https://docs.kernel.org/accounting/psi.html), shed new bulk admission and trim idle buffers/checkpoints while preserving completion/control capacity. A logical permit returned to a budget does not prove the allocator or kernel released resident pages. Test pressure-driven trimming and its refill latency explicitly.

Focal's record reports 1K claims/reads at 1,589 minor faults/22.9 MB max RSS, 2K at 2,256/33.8 MB and 10K at 7,580/121 MB. Its inferred “667 faults/1,000 claims means 2.7 MB per claim” has a unit error: even at 4 KiB that is about 2.7 KiB/claim; at 16 KiB it would be about 10.7 KiB. Page faults are not necessarily distinct retained pages. Use the raw [workload-specific table](../../../focal/docs/qualification/allocations-2026-09-29.md#L193), and measure Mantle independently under network/device pressure.

### 12.5 Performance gates that reveal resource movement

Benchmark fresh and warmed paths, stable sessions and churn, cancellation, slow readers, stalled storage, cold restart and workloads near admitted RAM. Report per-operation allocation/reallocation counts and requested bytes; peak/live/retained capacity; payload-copy ratio; RSS/working set and allocator retention; minor/major faults; CPU cycles/ns per byte; cache/TLB misses where available; p50/p99/p999 with enough samples; useful throughput and thread/task counts. Include socket/TLS/runtime buffers and kernel-backed memory in the envelope.

Measure all participating workers or an isolated process: a caller-thread allocator counter misses log/chunk/IO-owner allocations. Carry a measurement epoch across owners, avoid logging inside it, and exercise refused/retried/cancelled operations. Add same-session batch size sweeps, adjacent cached/cold entry batches, multiple stalled snapshot recipients, 1/16 warmed volumes and many mostly dormant ranges. Fallible Vec reservation does not make infallible map/Arc/Clone allocation recoverable; fund those owners before admitting work.

Set zero-allocation gates only for explicitly warmed bounded operations where feasible, and separate cold growth/refill costs. Require no post-admission payload-proportional reallocation on steady streaming paths, and a measured bound on copies/peak bytes per coding scheme. Publish before/after data and regression limits. “Drastically faster” remains a hypothesis until an equivalent complete operation demonstrates lower CPU/memory/latency without moving retention into an unmeasured layer.

A cited value from another product establishes provenance; it does not establish optimality on this deployment. ## 13. Congested, unstable and extremely low-bandwidth networks

### 13.1 Largest PMTU is not the best latency operating packet size

Slates' [DPLPMTUD](../../../slates/crates/transport/src/pmtud.rs#L1) discovers usable sizes, handles local EMSGSIZE, bounded failed probes, black-hole fallback and later increases. Its recorded loopback transfer improved **1,625→7,840 Mbit/s** after confirming 9,209-byte datagrams; its floor-path grids found differences within measured noise. [Adaptive reorder tolerance](../../../slates/crates/transport/src/reorder.rs#L1) raised recorded reordering-path goodput **2.54→5.39 Mbit/s** without raising steady ping p99. These are valuable mechanisms with [recorded evidence](../../../slates/docs/wip/BENCHMARKS.md#L550), not WAN/object-storage throughput predictions.

Keep PMTU as a safety ceiling, and derive the **operating bulk packet/burst size** from path rate, latency budget and receiver resources. Serialization alone takes `8 × packet_bytes / link_bits_per_second`. At 8 kbit/s, 1,200 bytes takes **1.2 seconds**; a 9,209-byte packet takes about **9.2 seconds**, before loss, queueing and reverse ACK delay. Strict priority cannot preempt a bulk packet already queued/transmitting. Large UDP bursts/GSO segments and deep kernel/NIC queues can similarly defeat application priority.

Standard QUIC requires a path supporting at least 1,200-byte UDP payloads and padding for specified Initial/path-validation datagrams; that is not a mandate that every established 1-RTT packet be 1,200 bytes. Preserve protocol minima while permitting smaller established application packets and an airtime-bounded bulk quantum. A path whose supported PMTU is below the minimum needs explicit refusal/another declared supported transport, not silent unsafe fragmentation. See [RFC 9000 §§14–14.1](https://www.rfc-editor.org/rfc/rfc9000.html#section-14).

The current Slates pacer quantum has a two-datagram floor and selects large packets up to discovered PMTU. Its thin-link bake-off already records Copa ping p99 **678 vs 289 ms** for NewReno at 64 kbit/s/no loss. Focal records **134 vs 78 ms** at 1 Mbit/s/20 ms against CUBIC. A geomean winner can lose on exactly the links the user requires. Add an airtime/fresh-control test before adopting these operating choices unchanged.

### 13.2 Treat sibling Copa results as evidence for implementations and workloads

Slates selected Copa δ=0.5 from 57 scenarios after fixing several controller/transport defects; δ=0.04 failed RTT fairness, and its BBR/Reno/CUBIC implementations stalled on certain high-BDP loss paths. Its scheduler grid selected strict priority; weighted scheduling's failure was explicitly suspected to be an implementation bug. Focal selected Copa against Quinn alternatives on its own 30-path grid and delegates pacing to Quinn. See [Slates bake-off](../../../slates/docs/wip/BENCHMARKS.md#L490) and [Focal network study](../../../focal/docs/archictecutre/27-consensus-roadmap-and-slates-port.md#L463).

Those results do not prove that all BBR/CUBIC/deficit schedulers are intrinsically inferior or that Copa maximizes every Mantle workload. Copa's [primary paper](https://www.usenix.org/conference/nsdi18/presentation/arun) concerns a congestion-control law; complete protocol behavior depends on sampling, pacing, feedback, flow windows and implementation. Run Mantle's actual control/append/snapshot/chunk/repair mix over asymmetric links, competing external traffic, incast and variable capacity. Preserve measured-and-rejected records and investigate anomalies before turning them into algorithm conclusions.

Validate true wire-byte inflight/pacing accounting, ACK-delay correction, monotonic clocks, app-limited detection, bandwidth transitions, idle restarts and repeated blackouts. Detect reordering-induced spurious loss and adapt thresholds with bounded history; keep PTO able to recover a real tail loss. Reordered retransmissions and delayed acknowledgements must never create duplicate application effects. PMTU probes need bounded airtime/CPU/memory, and their losses must not be interpreted as ordinary data congestion. Follow the selected implementation's [RFC 9002 loss/pacing contracts](https://www.rfc-editor.org/rfc/rfc9002.html#section-6) and [RFC 8899 probing model](https://www.rfc-editor.org/rfc/rfc8899.html).

### 13.3 Priorities need admission, useful reserves and starvation protection

Separate votes/heartbeats/durable completions, metadata/renewals, user reads/writes and background snapshot/repair/rebalance. A peer must not choose an unlimited privileged class just by setting a stream ID. Authorize message kind and bound each class by bytes, work, age and tenant. Strict priority protects urgent work only when urgent offered load is itself bounded. Under sustained priority floods it can starve repair, cleaning or bulk forever and thereby weaken capacity/durability.

Use reserved completion/control opportunities plus minimum sustainable repair/cleaning progress and bounded per-tenant fairness. Test competing high-priority clients, tiny-message floods, cancellation storms and worst allowed replication fanout. Rate-limit resends at both application and transport layers; do not run an unbounded Raft retry loop on top of QUIC retransmission. Coalesce obsolete heartbeats/credit state only where protocol authority makes replacement safe; preserve votes, reads and proposal disposition. Reserve egress/NIC/kernel queue capacity, not just logical stream slots.

A large snapshot frame treated as Control can starve elections despite stream priority. Classify by semantics and actual work, stream large evidence out of band and require bounded slices at encoding, crypto, parsing and apply. Chunk/block checksums and AEAD are mandatory; dropping integrity work for speed is not a network optimization.

### 13.4 Match BDP windows to memory and sustainable durable consumption

The useful window must cover a measured BDP where feasible, but it must fit aggregate admission: `window ≤ min(stream budget, connection share, node remaining budget, admitted sink capacity)`. At 100 Mbit/s/300 ms BDP is about 3.75 MB; at 1 Gbit/s/100 ms it is 12.5 MB. A single 1 MiB stream is therefore flow-limited. Focal's recorded multistream design improved these cases, but parallel streams share congestion and multiply framing/memory overhead; they do not create bandwidth.

Receiver credit must track movement into another **independently budgeted** stage. Eagerly reading QUIC into a disk queue and granting fresh credit can accumulate an unbounded NIC→decoder→EC→disk backlog. Conversely, waiting for a whole chunk to become durable before releasing any credit can deadlock when the window is smaller than the chunk. Reserve a bounded whole-chunk assembly slot and transfer ownership into it, or define durable streaming fragments with verified finalization. Application Stored follows the required durable fence; a transport ACK only establishes transport receipt.

For slow/stalled readers, count sender source bytes, retransmission bytes, response bytes and retained parents until completion/reset. Bound concurrent streams and dials by live bytes as well as count. If the admitted working set no longer fits during bandwidth collapse, reduce data credits/offered load and stop admitting new bulk work; continue funded control/completion/cleanup. Under overload, return the documented S3 error/retry contract while keeping unknown outcomes recoverable.

### 13.5 Brownouts, reconnect and Raft timing must share an explicit progress contract

Fixed 5-second calls, 10-second idle bounds or 300–2,000 ms probes from sibling applications are not universal Mantle defaults. A healthy 8 kbit/s peer sending multi-kilobyte handshake/evidence can exceed them. Derive progress deadlines from bytes remaining, measured rate/tail delay and an overall caller budget; cap them and account their memory. Separate local admission wait, sender queueing, remote processing, disk fence and network RTT. A queued operation or starved local executor is not proof the peer died.

Focal's default [nonbulk call deadline](../../../focal/crates/focal-wire/src/transport.rs#L774) is **five seconds and applies to Raft traffic**. A 128 KiB body alone needs at least **16.384 seconds at 64 kbit/s**, before headers, competing traffic, loss or persistence. That can become an unknown/lost outcome on a functioning slow link. Its 1 Mbit/s-and-up qualification does not cover this condition. Negotiate/bound append bytes and transfer progress with the rate/deadline policy, preserve durable retry identity, and test Raft append/snapshot behavior at the required 8/16/64 kbit/s rates.

On rate collapse/outage, bounded backoff and jitter prevent reconnection/election storms. Keep reusable healthy sessions where authority permits, but revalidate certificate/range/route epochs after restart/migration. Resume large transfers with authenticated bounded offsets/chunk identities and integrity checks; speculative duplicate attempts require a measured delay, shared byte budget, exact durable operation identity and loser cleanup. Unlimited hedging on a congested link makes congestion worse. A retry must not invent a new operation identity for an uncertain prior mutation.

Raft must remain safe under asymmetric partitions, minority reachability, lagging durable storage and leader moves. A low-bandwidth path may simply be unable to sustain the admitted append rate or election SLO. Admission and deployment qualification must say so. “Maximal performance” includes useful degradation and bounded recovery; it cannot promise progress without a quorum or acknowledge before required replicas are durable.

## 14. Integrate media adaptation, physical-device ownership and the object path

### 14.1 Per-volume tuning cannot optimize or bound a shared physical device

Each [Volume start](../../crates/chunk/src/volume.rs#L229) creates writer/cleaner and optional scrubber threads; [write_together](../../crates/chunk/src/writer.rs#L1427) creates scoped write-region threads per batch. At 100 scrubbed volumes that implies 300 persistent threads before serving/coding, plus batch workers. The current overlap is a measured optimization on the developer's machine, and still joins writes before full flush. Preserve the flush guarantee while measuring a bounded reusable/native-async issue population.

Client read Gate is per volume. Cleaner/scrub/cold-log reads bypass it; WAL and metadata engines can independently flush files on the same backing device. Thus measured client depth is not actual aggregate QD. Pool limits count free cached buffers, not all active ones, and chunk queue room can return before the executing batch ends. A logical volume/file/partition is not necessarily an independent queue or failure domain.

Create one scheduler/admission authority per resolved bottleneck, retaining a storage graph for shared drive/controller/RAID/filesystem/remote link ancestors. Child budgets fund volumes, WAL, Engine, foreground, cleaner, scrub and repair. Account outstanding IO count/bytes, estimated device service time, flushes, live payload/encoding buffers, CPU, reserved free extents and oldest work. Acquire before allocating/coding; transfer credits atomically between bounded stages. Reserve WAL/renewal progress and enough background progress to sustain space/durability.

A flush fence may acknowledge only writes known complete before that fence, under the actual backend's persistence contract. A flush of one file does not automatically certify another file's durability. Failed/ambiguous flushes fence the affected domain; unknown late completions cannot publish success. Enforce one active owner per opened volume/log resource, including alias paths/incarnations. Stalled device calls must not stop healthy devices or make indefinite shutdown look successful.

### 14.2 Detect capabilities and shared topology, then measure the operating plan

[Identity](../../crates/disk/src/identity.rs#L108) already separates medium/interconnect and optional capabilities. Linux recognizes NVMe fabrics and walks composite members. Retain that distinction: NVMe is an interface; SSD is a medium; remote NVMe and a laptop SSD have different bottlenecks. Extend stable backend identity, represented raw-device capacity, actual file-specific direct-IO alignment, topology completeness, firmware/caching generation, persistence semantics and profile provenance. `nr_requests` is a hint, not an optimum hardware queue depth.

Bound the total composite graph walk, deduplicate members/aliases, detect cycles and report truncated/unknown topology. Several files on one SSD cannot establish independent redundancy. Device write-cache strings and FUA hints do not by themselves establish power-loss durability through a filesystem/RAID/remote server. Known unsupported host-managed zone semantics must be rejected before formatting; do not claim sequential zones because the configured segment happens to be 256 MiB.

Persist a versioned DevicePlan separating immutable format choices from runtime issue policy. Derive read/write widths, batch bytes/deadlines, direct/buffered/preallocation policy, cleanup/repair shares and reserve headroom from capabilities **and mixed-load measurements**. Invalidate after backing-device/filesystem/firmware/topology or sustained-state change. Online adaptation needs bounded probes, confidence, hysteresis and the last valid safe plan. Never weaken durability based on a device label.

| Device class | Measurements that must choose the plan |
|---|---|
| Laptop NVMe/Apple SSD | Tiny durable objects, QD-to-saturation read/write mixes, interleaved full WAL flushes, first allocation/overwrite, energy/idle spin, sleep/wake and pressure |
| Server NVMe/PLP SSD | Several volumes/controller sharing, NUMA and coding load, batch/deadline/issue-width sweep, sustained near-full/GC/thermal states, failed and late completions |
| SATA/SAS SSD | Smaller queue mixes, overwrite/GC, discard/prewrite break-even, endurance/write amplification, controller cache and power-loss semantics |
| HDD | Seek/transfer crossover, adjacent ranged-read coalescing, distant WAL/index writes, sequential background IO under random foreground, slow sector/error recovery |
| RAID/virtual/network/FUSE | Shared-member/noisy-neighbor saturation, remote cache/RTT, direct fallback, detach/reconnect/replacement behind stable paths and incomplete topology |
| ZNS/host-managed SMR | Actual zone size/capacity/open/active limits, append result/write pointers, reset/ownership/recovery and refusal before unsupported writes |

### 14.3 Cleaning and repair rates must agree with durability promises

Mantle's cleaner already derives runway from observed arrival/reaction/victim cleaning cost. Extend that to accepted concurrent WAL/Engine/scrub/repair work and degraded-device throughput. For a victim live fraction `u`, relocation bytes per reclaimed byte are approximately `u/(1-u)`; at `u=0.9`, roughly nine relocation bytes reclaim one, before padding/checkpoint overhead. Sustained near-full workload can therefore destroy the fresh-device throughput assumption. Measure actual amplification and refuse/throttle workloads without sustainable reserve.

P06's repeated live-byte aggregate is especially serious at large capacities: for a 20 TiB data area, 256 MiB segments and 1 MiB windows, a pass performs about **1.72 trillion segment visits** solely for that sum. Maintain verified incremental aggregates and bounded candidate indexes; revalidate victim incarnation/live data before relocation. Preserve empty-device pacing. Damage-triggered zero-pause scrub across many devices also needs aggregate urgency/fairness; scanning is detection, not repair.

For lost capacity `D`, useful reconstruction bandwidth `B`, `T_repair ≥ D/B`. Reconstructing one missing RS(k,m) chunk of size `c` can require `k·c` source bytes, plus coding/checksum, target writes and full flushes. Source disks/NICs, decoder CPU/memory, cross-zone links, target capacity and foreground reservations all matter. Qualify the largest admitted node/rack/zone loss and a second failure near capacity before feeding a one-hour repair rate into an eleven-nines model. The actual failure-domain occupancy/repair placement must match B09's model qualification.

### 14.4 Object-level gains require ownership, API and key correctness

Use healthy systematic shards and only necessary authenticated segments for range GET. Convert complete-vector [pieces/spans](../../crates/gateway/src/layout.rs#L164) planning into bounded iteration for multi-TiB objects. Copies sharing and in-place AEAD are already efficient; measure tiny-object replication/append packing against wide EC fanout rather than enforcing one layout for every size.

Packing, recoding, deduplication and zero-copy COPY introduce shared physical ownership. Do not add them before authoritative adoption/release/retention/reader fences exist. Current COPY requires fresh block identities under its stated ownership model. A recode needs new layout identity, verified chunks, atomic Block publication and fenced old-layout retirement; a key/epoch field alone is not that protocol. CompleteMultipartUpload nests part files, so MAX_EXTENTS is not a 48.8-TiB object incompatibility; preflight each PUT/part's permitted length and manifest/renewal work instead.

Backups need a consistent metadata/data/key cut and protected references while export streams. Uncoordinated listing plus GET is not a consistent backup under delete/GC. Restore must recover wrapped key generations, ownership/placement identities, versions/retention and chunk integrity without ordinary metadata exposing root keys. Test old-generation keys after rotation and partial-cell loss. Intact ciphertext without the right key authority is unreadable data. Ciphertext migration can avoid resealing only when file/key/AEAD identities and policy remain valid; cross-object COPY has different identity requirements.

## 15. Laptop-to-global capacity and qualification requirements

### 15.1 Publish a measured envelope at each layer

Global capacity is independent bounded partitions multiplied by measured partition capacity, subject to shared-device/network/control/repair limits. It is not one Raft benchmark multiplied by an arbitrary node count. A laptop must execute the same acknowledgement, checksum, encryption, ownership and cleanup contracts with one member/device and honestly report single-device durability. A regional cell must state maximum groups/objects/placement entries/connections, total live bytes, foreground SLO and admitted failure size. Fleet growth adds cells and routing/migration authority; it should not require a worldwide quorum per object.

At minimum, use these explicit resource/cost models, then validate them against actual RSS/IO/CPU:

- `M_node = shared Engine/cache + Σ(range core/index/cache/session/staged bytes) + Σ(device live/cached buffers) + transport raw/reorder/retransmit/app bytes + gateway/coding/snapshot/runtime memory`.
- Per-peer network ceiling is a share of that node budget, not a window independently multiplied by every connection. Kernel socket queues and registered/pinned pages require accounting too.
- With `L` leaders and replication factor `r`, leader heartbeat sends alone are approximately `L(r−1)/h` per second at heartbeat interval `h`, before replies/append/read/repair traffic. A hypothetical 100,000 local groups, one-third led locally, `r=3`, `h=0.1s` already implies roughly 667,000 leader heartbeat sends/s. This is a stress illustration, not an achieved density.
- Naively ticking 100,000 groups at 10 Hz visits a million groups/s even when idle. Event-driven deadlines, safe quiescence and batched peer traffic need an explicit per-group quorum wake/recovery protocol; sharing node liveness cannot simply replace each group's ReadIndex/lease rules.
- A full fleet mesh has quadratic peer-pair state. Bound cell neighborhoods, placement-driven sessions and hierarchical control dissemination; one shared socket reduces ports, not the number of all-to-all relationships.
- Router-map refresh cost scales with gateways × map bytes / refresh interval. Use bounded versioned deltas/snapshots and stale-route fencing; include restart/admission storms.
- Repair and migration consume source and destination capacity together. Reserve disk/NIC/CPU/memory/space at node/rack/cell scope before launching work; foreground success cannot rely on starving this work indefinitely.

Bound total **and active** groups separately. Many idle descriptors still consume core/index/session/cache/timer memory; many hot groups consume scheduler/flush resources. Compare one shared Engine/cache with per-range namespaces against one engine/cache/manifest set per tiny range. A timer wheel and shard-local slabs are useful references, but fixed capacities need actual admission/refusal behavior and cleanup through restart.

### 15.2 The simulation must exercise composition and non-vacuity

Current Mantle consensus simulation is one three-member group with two keys and Model engines. Twenty thousand seeds are not twenty thousand concurrent groups. It drives replicas synchronously and sends outputs afterward, so it cannot witness early-message overlap or independent-device progress under one blocked flush. Existing chunk crash tests, metadata collection models and sibling protocol simulators test valuable separate contracts.

Add a deterministic **many-group** host using the actual phased owner, shared-device scheduler and selected peer transport. Inject delayed/failed/ambiguous flushes, completion loss, stopped workers, credit starvation, stale callbacks, cancelled clients, corrupt snapshots and receiver pressure. Check every event's aggregate budgets, every admitted request's disposition, reachability/ownership, applied-prefix reads, durable voting, repair progress and eventual token return. Include hot/cold groups, one abusive tenant, correlated elections, slow HDD and one healthy device continuing while another stalls.

A passing fast-path test must count actual use: ahead batches, shared flush coverage, early leader sends, reused buffer slots, fewer copies/allocations, prefault slices, reorder adaptations and chunked snapshots. Mutation tests should break the relevant fence/accounting/ownership rule and fail. Keep minimal crash histories and rejected experiments; avoid a serial oracle that silently repeats the implementation's faulty assumptions.

## 16. Massive objects: multi-terabyte datasets and hundred-gigabyte video

### 16.1 The supported unit must be a durable multipart object

Large-object support means bounded transfers that finish, recover, verify and reclaim correctly over hours or days. Accepting a u64 body length is insufficient. The current representation is promising: each uploaded part is a separately encrypted File of Blocks; the final object is a File of part Files. Completed parts have durable Name ownership, so an unfinished multipart object does not require retaining every block in a gateway or continuously renewing every completed part's Block handover. The provisional block renewals apply to the currently uncommitted part. Preserve this distinction when sizing the runtime.

[File::MAX_EXTENTS](../../crates/meta/src/file.rs#L18) limits each file to 10,000 extents. A flat file would top out at about **77.515 GiB for Copies** or **702.515 GiB for RS(9,6)** with the current authenticated block geometry. A direct hundred-gigabyte Copies PUT therefore cannot finish through that representation, even though the constructor accepts the length. Correct S3 integration uses multipart above the supported single-request size; nested part Files avoid the flat ceiling. B08 requires refusal before writing an unsupported body, not a late manifest failure.

The current S3 target is up to 10,000 parts of at most 5 GiB, approximately **48.8 TiB per object**; nonfinal parts are at least 5 MiB. Objects beyond the supported limit need an explicitly separate dataset manifest of multiple objects, with its own publication and retention semantics. Do not promise atomic multi-object publication merely because the final manifest fits in one Name transaction. [AWS multipart limits](https://docs.aws.amazon.com/AmazonS3/latest/userguide/qfacts.html).

| Workload example | Average part size required if using all 10,000 slots | Implication |
|---|---:|---|
| 500 GiB video | 51.2 MiB | Indexed range playback and bounded parallelism still need measurement |
| 2 TiB dataset object | 209.7152 MiB | Smaller uniform parts exceed the protocol count ceiling |
| 5 TiB dataset object | 524.288 MiB | 256 MiB parts would require 20,480 and cannot complete |
| 10 TiB dataset object | 1,048.576 MiB | Retry unit and transfer duration become substantial on slow paths |
| 10,000 × 5 GiB | 5 GiB | 48.828125 TiB by arithmetic; maximum manifest/key cardinality requires qualification |

These are protocol-derived feasibility floors, rounded up to whole bytes in an implementation, rather than selected tuning values. For a known final size S, the optimizer must choose a legal part size p satisfying `ceil(S/p) ≤ 10,000`, and reserve completion capacity before transferring data. Unknown final sizes need a declared upper bound, a conditional growth policy or multi-object dataset representation; silently increasing future part sizes cannot undo already-used part numbers.

### 16.2 Part size and concurrency must follow rate, failure cost and memory

Part size is a retry/metadata unit; it is not a requirement to buffer an entire part. Streaming a 5 GiB part should use the same bounded block/segment slots as a smaller part. Increasing concurrent parts without a node-wide byte/work allowance multiplies AEAD/EC buffers, chunk RPCs, manifests, renewals and device queue pressure.

The ideal transfer floor is `8S/R`. A **2 TiB object** takes at least **48.87 hours at 100 Mbit/s, 4.89 hours at 1 Gbit/s, 29.32 minutes at 10 Gbit/s, or 2.93 minutes at 100 Gbit/s**. These exclude all overhead, storage, replication and competing work. At 64 kbit/s the floor is about **8.7 years**: support for extremely slow links must mean useful bounded progress/resume and honest feasibility, not a multi-terabyte completion SLO independent of bandwidth.

A 256 MiB part alone takes **9.32 hours at 64 kbit/s** or **21.47 seconds at 100 Mbit/s**; a 5 GiB part takes **7.77 days** at 64 kbit/s. A short whole-request deadline guarantees repeated wasted transfers. Smaller parts reduce retransmission exposure but increase completion rows/transactions and eventually hit the 10,000-part ceiling. Choose part and internal transfer/checkpoint sizes separately, based on observed rate, loss/outage distribution, source seek cost and the permitted replay bytes/time.

Use adaptive bounded concurrent parts/block flights to cover BDP and durable pipeline latency. Cap aggregate useful bytes, coding work and sink reservations; decrease offered load under congestion or slow durable storage, and increase it with measured headroom. Parallel parts may use independent gateways/disks where placement permits, but authenticated source identity, object ownership and tenant fairness still apply. A laptop should select a small working population; a 100 Gbit/s server needs a measured wider pipeline rather than thousands of unconditional tasks.

**Required per-upload optimizer.** Given known size S, the implementation should determine a selected size plan and resulting count from measured conditions. Define the objective explicitly: for example, minimize expected durable completion time while satisfying operator latency, durability, fairness, memory and replay-cost requirements. If efficiency/resource use is another objective, publish its constrained/Pareto tradeoff; invented numerical weights cannot establish a universal optimum. An upload size and network RTT alone are insufficient inputs.

Let the plan contain client-visible part sizes `p_i`, internal block/shard geometry, transfer-frame size and admitted concurrent flights w. Measure effective useful goodput g; RTT/queue-delay distribution; outage/interruption and recovery distribution; request/metadata setup and durable publication cost h; coding/hash CPU and copy/fault costs; path MTU; source/sink transfer curves; and available aggregate byte/work credits. Choose the feasible plan minimizing measured/modelled cost, and derive `N_parts = ceil(S/p)` for a uniform plan or `sum(p_i) = S` for variable parts. Derive Block/shard/frame counts independently from the encoded layout. The 10,000-part ceiling constrains feasibility; it does not choose the optimum.

For a transparent starting model, suppose interruptions are independent Poisson events of measured rate λ, useful transfer rate g is stationary, a failed part must restart, and h is fixed per-completed-part overhead outside that restart interval. Transferring p bytes then has expected restart time `(exp(λp/g) − 1)/λ`; minimize `C(p) = h/p + (exp(λp/g) − 1)/(λp)` over legal sizes. Under the additional rare-interruption condition `λp/g ≪ 1`, `C(p) ≈ 1/g + h/p + λp/(2g²)`, giving the interior candidate **`p* ≈ g × sqrt(2h/λ)`**. Its numbers come from measurements and the equation, not an arbitrary MiB constant. Evaluate the exact cost at the feasible boundaries/candidates and derive the count; at λ→0, metadata/setup cost favors larger parts until another measured constraint binds. If overhead also restarts, change the model accordingly. QUIC packet loss normally causes retransmission within the existing stream; raw packet-loss percentage is not the whole-part restart hazard λ. Correlated outages, changing bandwidth, resumed internal fragments and concurrent disk contention require their own empirical model; this illustrative derivation is not a universal network theorem or an implemented optimizer.

Include hard constraints on legal part sizes/counts and supported object size; maximum safe encoded manifest/Entry; permitted request/replay duration; exact peak ownership under w; coding/alignment/key limits; durable sink bandwidth/queueing; and funded control/repair progress. If these cannot all be satisfied, return the reason and best supported degradation/alternate dataset plan. No optimizer can make a below-capacity path sustain an infeasible offered load. Streaming keeps the memory constraint tied to working windows rather than whole p, but does not remove replay/time or manifest costs.

Use a bounded candidate search over legal layouts and measured change points, with confidence/error bounds and a documented optimality gap. Fit/revalidate using actual upload progress and controlled bounded exploration; test predictions against held-out traces, stationary optima and transitions. Change unstarted future parts/blocks or concurrency when evidence supports the benefit exceeding its measured switching/replay cost. The estimation horizon, confidence threshold, hysteresis, exploration budget and safety margin also need an SLO/statistical/resource derivation; hard-coded multipliers merely move the arbitrary constant. Record inputs, selected plan, predicted/observed costs and reason for every change.

Optimize the discrete count as well as the continuous size: for stationary conditions and a fixed multipart model, enumerate the feasible part counts bounded by the protocol, evaluate the corresponding aligned partition including its actual final-part cost, and compare admitted concurrency plans. For larger internal search spaces, exploit proved convexity/monotonicity or use bounded search that reports its remaining cost gap. Rounding one continuous candidate without checking count/alignment boundaries is not an optimum proof. The selected size/count should be deterministic for the same measured state, constraints and policy version; predicted costs that overflow or lack evidence must produce an explicit uncertain/infeasible result.

The standard S3 client chooses its UploadPart boundaries. Expose measured recommendations/transfer-manager policy and enforce admission, while optimizing internal transfers independently; the server cannot silently renumber or resize an accepted part. Current [Layout](../../crates/gateway/src/layout.rs#L55) assumes uniform per-file arithmetic geometry. [BlockHeader](../../crates/meta/src/record.rs#L309) already records length, k/m and chunk_len, and extents record lengths. Adaptive geometry should use authoritative extent-driven addressing and immutable recorded layout/epoch per block, with compatible readers/repair/GC. AEAD segment size remains a format decision until a justified versioned encryption change is designed; physical write batching and transport frames can adapt without re-encrypting existing data. Live adaptation must never reinterpret committed bytes under a newly selected size.

### 16.3 The current block publication path limits single-part throughput

[Put](../../crates/gateway/src/put.rs#L250) retains one Going block plus a Waiting block. [go](../../crates/gateway/src/put.rs#L500) requests placement, [placed](../../crates/gateway/src/put.rs#L598) sends the chunks in parallel, [stored](../../crates/gateway/src/put.rs#L625) waits for **every prescribed chunk** to become durable, then asks for Block publication. Only [recorded_block](../../crates/gateway/src/put.rs#L673), after that answer, starts the next waiting block. Body filling can overlap; multiple block placement/storage/publication chains cannot currently overlap within one part.

For full plaintext block size B and that chain's latency T, single-part throughput is bounded by approximately `B/T`, as well as CPU/network/media. RS(6,3) holds **50,266,112 plaintext bytes per full block**. At T=300 ms the latency ceiling alone is about **167.6 MB/s, or 1.34 Gbit/s**, independent of a faster NIC. Filling a 10 Gbit/s plaintext path at that latency needs roughly **eight independently progressing blocks**; 100 Gbit/s needs roughly **75**, before additional coding/queueing. These are source-derived illustrative bounds, not measurements or instructions to allocate 75 maximum blocks on every laptop.

Generalize Going into an admitted bounded flight window with per-block ownership/disposition, bounded completion order, placement prefetch and paced chunk transfers. Compute a candidate window as `ceil(target_plaintext_rate × observed_chain_latency / B)`, capped by memory/CPU/device/network reservations. Batch independent Block metadata updates through shared WAL receipts where safe. Keep Name publication behind validated body/checksum and complete durable File ownership. Requiring all prescribed chunks before Block publication currently establishes the intended initial redundancy; acknowledging after only k RS chunks would be a different durability/service policy requiring a proof, not a harmless speed switch.

At **100 Gbit/s plaintext**, the payload rate is 12.5 GB/s. RS(6,3) generates approximately **18.75 GB/s chunk payload**, while Copies(3) needs approximately **37.5 GB/s**, before authentication tags, checksums, network headers, repair and cleaning. Gateway NIC egress, coding/crypto/hash cores, DRAM copy traffic and distributed disk bandwidth must all fit this expansion. Avoid routing bulk bytes through Raft or a single metadata leader; only bounded descriptors/authority belong in that path.

### 16.4 Resume requires persistent progress and immutable operation identity

Standard multipart permits independently uploading/retrying parts and retaining completed parts until completion or abort; it does not make an arbitrary offset within UploadPart a resumable standard request. Keep a durable client/transfer-manager record of upload ID, source identity/length, part number/range, acknowledged ETag/checksum and completion state. ListParts can reconcile uncertain progress, with pagination and exact part identity, while the transfer manager retains its authoritative selected parts. [AWS multipart behavior](https://docs.aws.amazon.com/AmazonS3/latest/userguide/mpuoverview.html).

An interrupted public S3 part may need retransmission from its start. A separately supported internal resumable protocol can avoid resending already durable chunks between gateway and storage, and an optional explicitly documented client extension can support finer-grained resume. Persist a bounded transfer/attempt manifest, immutable file/block identities, verified offsets/checksums, and received/durable/published states. A TCP/QUIC ACK, bytes written, a completed chunk, a committed part and a committed object are different progress points; expose useful durable progress without telling a client its object exists early.

After uncertain replies, retry the same immutable operation or reconcile its durable disposition. A transport loss cannot authorize a new conflicting attempt to reuse encryption state. Each changed/replaced part needs a fresh file/data-key incarnation; resumed ciphertext must be identical to its recorded attempt. Preserve the [nonce/index/last-segment binding](../../crates/s3/src/seal.rs#L155). Persisting only a byte offset or serializing an opaque digest context is insufficient for source-change detection, crypto identity and crash-safe hash recovery.

Download resume must pin a version/generation across all ranges, using a supported immutable version or correctly evaluated strong conditional predicate. Reopening the current key after each disconnect can silently stitch bytes from different object versions. Source files need equivalent identity/length checks during upload; changed source data must fail or create a new attempt. Support credential/certificate/key-generation renewal, route retirement and gateway restart over transfers longer than their initial authority lifetimes, without treating a still-valid completed part as garbage.

### 16.5 Manifest and renewal work must be admitted independently of payload bytes

Two buffered blocks do not bound the recorded-block map or renewal work. Copies needs **646 Blocks for one legal 5 GiB part**; RS(9,6) needs **72**. With a hypothetical 60-second handover and quarter-period renewals, a stalled near-complete Copies part can require about **43 renewals/s**, before retries. Many slow simultaneous parts multiply this load even when payload throughput is tiny. Use an indexed deadline scheduler, bounded/jittered renewal batches and reserved durable renewal/control capacity; do not scan/enqueue every recorded block in one actor turn. Expiry must return a recoverable refusal and clean orphan data safely, not publish a damaged part.

A completed outer File can have 10,000 part extents. Their current encoding is roughly **340 KB**; a Name Complete with 10,000 ordinary 32-character ETags is roughly **540 KB**, plus other fields and Entry framing. The service's caller-supplied [max_entry_bytes](../../crates/range/src/replica.rs#L40), WAL frame/retention capacities and command-work bounds must admit that exact worst supported command. The 64 KiB setting in tests is not a production default. Check encoded bounds before expensive finalization or define a durable staged manifest/finalize protocol whose crash/reclaim semantics are modeled. A partial sequence of published extents must never expose a partially completed object.

The [Name completion](../../crates/meta/src/name.rs#L1415) validates listed part presence, ETag, exact file identity and minimum nonfinal size, then trusts gateway-supplied object size/ETag/checksum/composite file. The production completion driver must derive these from verified authoritative parts, validate the checked sum and legal aggregate limit, and reconcile replacement/abort/conditional completion. Current helpers and corrected B02 ownership are a foundation; there is no complete driver whose multi-terabyte completion is certified.

Admission must enforce part number/size on every route, including internal callers: metadata PutPart currently accepts u16 numbers/u64 sizes, while the public Complete XML parser supplies only part-number/ordering checks. Preserve initiation checksum algorithm/type and validate its mode-specific consecutive numbering, part values and aggregate. A merely sorted part list does not establish checksum-mode conformance. Do not let an unvalidated internal caller invalidate the claimed 10,000-row completion/cleanup work bound.

### 16.6 Integrity must remain one-pass where its checksum algebra permits

[Checksum](../../crates/s3/src/checksum.rs#L1) already implements all ten current named algorithms, CRC full-object combination from part values/lengths, and multipart composite values. Preserve that efficient CRC algebra: successful completion should not reread multiple terabytes just to calculate a supported full-object CRC. Composite SHA/MD5 values are hashes of part digests, not the SHA/MD5 of the full concatenated plaintext. Validate exact length, part order, algorithm/type and header/trailer semantics before Name publication. A multipart ETag is not a universal content hash. [AWS integrity semantics](https://docs.aws.amazon.com/AmazonS3/latest/userguide/checking-object-integrity-upload.html).

Fuse mandatory passes where safe: update required hashes/checksums as bytes stream, encrypt admitted segments in place, compute chunk checksums during final coding/formatting, and avoid a whole-object reread. Measure actual MD5/hash, AES-GCM, RS and CRC costs together. The current PUT unconditionally computes plaintext MD5 for its ETag; CPU scaling and mode-aware ETag semantics must be resolved, rather than silently dropping a required digest for speed. Encrypted/authenticated data precludes a blanket sendfile or unmodified zero-copy claim; ownership transfer, direct final-buffer encoding and bounded scatter/gather are the concrete opportunities.

Each part's independent key and 64 KiB authenticated segments bound the crypto working unit. A 5 GiB part uses **81,920 segment seals**, with checked 63-bit segment indices. Define a reviewed per-key byte/invocation security budget; a wide counter alone is not its proof. Persist key generations and support recovery/rotation without losing old multipart keys. Range responses still verify every returned segment's AEAD and stored checksums; a full-object checksum cannot be recomputed from an arbitrary partial range alone.

### 16.7 GET planning and buffering must remain independent of object length

[Layout::pieces](../../crates/gateway/src/layout.rs#L167) returns a Vec for every covered block. The File extent API similarly materializes bounded pages, while a production recursive GET driver is still planned. Avoid collecting the entire object plan, all child Files or full reply bytes before first output. Use a seekable bounded cursor through outer part extents and each part's Block extents, with cached immutable/versioned descriptors, explicit byte/count permits and bounded lookahead. Open only active part keys; avoid one retained unwrap/key/reader per part.

Define and index **object plaintext prefixes separately from child stored offsets**. Data File extents/header lengths currently describe sealed bytes, and each multipart child independently rounds/tags its last segment and resets its key/index. Applying seal::plain_len to the combined stored length as if it were one encrypted File is incorrect. For a legal first part of `5 MiB + 1 byte` and a final one-byte part, this mistake interprets an extra tag as 16 extra plaintext bytes. Translate only within the selected child, verify its own final-segment bit/AAD/key, and seek by authoritative plaintext prefixes. Otherwise a tail seek can require opening/scanning 10,000 children or address the wrong range. No production recursive GET exists yet; this is an integration invariant, not a demonstrated live read corruption.

For video, qualify first-byte latency, sequential playback, seeks, tail metadata and many simultaneous viewers. For datasets, qualify footer/range scans, parallel row-group reads, shuffled training access and sequential export. Seek/coalesce at authenticated segment and physical-record boundaries, while returning the exact requested plaintext range. Prefetch based on observed access/media behavior and cancel obsolete seeks; full-record prefix reads (P01) and unnecessary EC materialization (P08) become expensive at this scale. HDDs benefit from bounded sequential runs; NVMe benefits from measured parallel spans. Do not force one access plan on both.

Parallel bounded range GETs and part-aligned downloads can improve aggregate throughput and reduce retry work, as described in [AWS performance guidance](https://docs.aws.amazon.com/AmazonS3/latest/userguide/optimizing-performance-guidelines.html). They must share source disk, network, tenant and coding budgets; unlimited range fanout can destroy HDD locality or saturate metadata. A slow HTTP reader must hold only its admitted window and pins, and cancellation must release those after outstanding kernel/network ownership completes.

### 16.8 Sustained storage, recovery and durability must be qualified at object scale

Measure bulk ingest long enough to exhaust SSD burst caches, reach thermal steady state, trigger writeback/GC and exercise near-full cleaning. Count physical writes, parity, index/checksum metadata, relocation and repair, not only accepted plaintext. Keep free-space and funded cleaning/repair reserves before admitting another large part. A transfer that fills a cell before its final manifest must fail/recover according to its documented reservation policy, not strand the cleaner or erase a live part.

Cold restart/index rebuild and scrub scale with physical chunk/fragment cardinality, not object count. Qualify checkpoints, scan bytes, memory, startup latency, corruption proof and reconstruction while foreground bulk continues. Parallel transfers need physical-device admission (§14), and recovery cannot eagerly clone every huge object/snapshot into RAM. For multi-day streams, key/root/checkpoint backup and GC ownership are as material as bandwidth.

A maximum 10,000 × 5 GiB multipart object creates **6.46 million Blocks / 19.38 million chunks for Copies(3)**, or **720,000 Blocks / 10.8 million chunks for RS(9,6)** with the current per-part geometry. Part boundary rounding matters; these are sums over actual parts rather than treating the whole object as one flat stream. Fragment slots, index heap/checkpoints, reverse rows and cleanup/repair work must fit the distributed placement envelope.

Default [max_fragments](../../crates/chunk/src/layout.rs#L47) is 2²²: its raw payload capacity is only **16 GiB at 4 KiB fragments, 256 GiB at 64 KiB, or 32 TiB at 8 MiB**, before overhead/reserves. Tiny network frames must not automatically become durable volume fragments. Derive fragment capacity jointly from admitted volume bytes/minimum durable fragment size and measured heap/recovery/checkpoint budgets. [Checkpoint](../../crates/chunk/src/writer.rs#L1250) collects all Put records into one Vec, even though the emitted frames are bounded; full 2²² index payload is approximately **304 MiB** at 76 bytes/Put, plus segment records/alignment and duplicate in-memory state. It holds the writer through the frames and two full flushes. Stream an immutable checkpoint view with bounded descriptors or prove another bounded publication path, preserving superblock/index durability and relocation ownership; measure foreground pause and recovery at declared cardinality.

The advertised durability unit must include whole objects: many independent Blocks compound a per-Block upper bound, and correlated rack/zone/key/metadata/software failures invalidate an independence shortcut. Use measured repair bandwidth and placement occupancy, then state the supported object-size/service-class envelope (§8.3/B09). Concurrent large uploads must not consume the bandwidth required to restore existing objects after a node/rack loss.
