# The metadata engine: RocksDB 11.8.1, converted to Rust

Status: design, 2026-09-30; phase P1 done. Sources: docs/research/24 (the port's contract,
cited as "24 §x"), docs/research/12 (RocksDB and ZippyDB, cited as "12 §x"), docs/research/23
(Meta's RocksDB enhancements); RocksDB at tag `v11.8.1`, commit `abeebd963`, cited as
`[R path:line]`.

The engine under a metadata range replica is RocksDB, converted to Rust as the crate
`mantle-engine` (`crates/engine`). Its definition of done is RocksDB 11.8.1's own formats and
behaviour: the engine reads every file RocksDB 11.8.1 writes in the configurations 24 §1.18
lists, and RocksDB 11.8.1 reads every file the engine writes. It runs as 12 §6.1–§6.2 describe:
one instance per range replica, many instances per process under shared budgets, and the WAL
off, with the per-disk Raft log (raft-log.md) as the only write-ahead log.

## 1. Why a conversion

Note 12 chose RocksDB as the engine: it alone had file-level snapshots, splits and moves
(checkpoint, ingest, column-family export and import), cheap range removal and budgets shared
across instances, with production evidence behind them (12 §5.7, §5.8 item 1). What it could not
meet came from the binding, not the engine (12 §5.7): the upstream C++ build does not issue the
full flush on macOS (`F_FULLFSYNC`) unless built with `HAVE_FULLFSYNC` (24 §2.2), so CLAUDE.md §6
fails there; the C++20 build with libclang breaks the cross-target lint of every target
(CLAUDE.md §7, 12 §5.8 item 3); and a C++ engine cannot run under mantle's deterministic
simulator, so crash and fault tests on it are not replayable (12 §5.7 row 9, CLAUDE.md §8).
Note 12 kept "a mantle-built LSM as the long-term option if RocksDB's build or behavior cannot
meet the gates" (12 §5.6, §5.8 item 4).

On 2026-09-30 the owner decided to take that option with RocksDB itself as the design: convert
RocksDB 11.8.1 to Rust inside mantle, in full. A conversion keeps what made RocksDB the choice
(its formats, its compaction behaviour, its years of production and of bug fixes, 12 §1.13) and
removes what the binding broke: the file layer is mantle-disk with the platform's full flush
(24 §2.2), the code lints and tests on all six targets like the rest of mantle, the background
work is schedulable by the simulator (24 §5 R17), and every failure is a typed error instead of
an abort or an unchecked read (24 §2.3, §5 R6). Note 24 is the specification the conversion is
checked against: the formats byte for byte (§1), the module map (§2), the phase order and its
tests (§3), the concurrency model (§4) and the risks (§5).

## 2. Format compatibility and the oracle

The engine is checked against the C++ build of RocksDB 11.8.1, the oracle (24 §3.0). The
engine never links it: the oracle's `sst_dump`, `ldb` and `db_bench` run as processes on files
each side wrote (CLAUDE.md §8), built outside the repository.

- **Two directions for every format.** The C++ tools open what the engine wrote and must print
  the same content; the engine reads a corpus of files the C++ build wrote. The corpus is
  generated by a script outside the repository, keyed by each file's SHA-256, and regenerated
  rather than committed. Its axes are the options that change bytes on disk (24 §3.0):
  format_version 2–7, the five checksum types, the compressions, the index and filter types,
  restart intervals, data-block hash index, range deletions, wide columns, blob files and
  separated key-value blocks, on x86_64 and aarch64.
- **Byte identity.** Given the same input and options, the engine writes the same bytes. The
  exceptions are the per-file randomness and time RocksDB puts in a table — wall-clock and
  identity properties, and from format_version 6 the random `base_context_checksum` — which the
  check reads from the oracle's file and gives to the engine's builder as inputs; the engine
  takes its clock, identities and context-checksum base from its caller for this reason.
- **Golden vectors** check the pure functions under the formats (hashes, checksums, coding),
  where a wrong answer passes every test that only writes and reads with the port: a filter
  keyed by a different hash answers "absent" for keys that exist (24 §5 R1–R2). A small C++
  program compiled from RocksDB's own sources prints each function's output over every input
  length 0–4,096, several seeds and random draws; the engine's tests recompute them (§6).
- **The test harness** replaces three C++ facilities (24 §3.0): `SyncPoint` becomes hook
  points compiled only in tests; `FaultInjectionTestFS` becomes mantle-disk's `SimFile` and a
  simulated directory (24 §5 R16); `DBTestBase` becomes a Rust fixture with the same helper
  names, so a ported test reads line for line against its C++.

Every RocksDB test of a ported module is ported test for test, with its name in snake_case and
its literals unchanged; a test is left out only when it exercises something the conversion
drops or replaces, and its file's port says which.

## 3. Rules the conversion keeps

- **Typed errors** replace `Status` (24 §2.3): `Corruption` (with what failed to decode; it feeds
  repair, CLAUDE.md §6), `Unsupported` (a format value the engine refuses, 24 §1.18),
  `InvalidArgument`, and in later phases `Io`, `Busy`/`Stalled`, `NoSpace` and `Shutdown`. Every
  C++ `assert` on a data path becomes a type invariant or one of these (24 §5 R6).
- **Stricter decodes, never stricter than RocksDB's writer.** Where RocksDB silently accepts
  bytes it never writes, the engine refuses them as corruption: a varint32 whose fifth byte
  carries bits above 2^32, a varint64 whose tenth byte is above 1 (24 §1.1), a checksum type
  byte outside 0–4 (RocksDB computes 0 and reports a mismatch). No file RocksDB wrote is refused.
- **No `unsafe`.** The engine is not an OS-interface file (CLAUDE.md §7); the memtable and block
  cache designs that avoid raw pointers are 24 §4.1 and §4.8, and R5 records the decision point
  if a safe memtable loses to the C++ one.
- **Module layout follows RocksDB's tree** in Rust naming (`util/coding.rs` converts
  `util/coding.h`, `table/format.rs` converts `table/format.{h,cc}`), and each module's comment
  names the files it converts, so a reader can hold the two side by side.
- **Integrity in memory** (research/31 §5.4, B13; D16). RocksDB's per-key-value protection,
  "per-key-value checksums in memtables and write batches", off by default upstream, is on in
  mantle's use, so a flip in a memtable or a batch between apply and flush is caught rather than
  written into a table under a fresh block checksum; its cost is measured against RocksDB with
  protection on in note 23's matrix. A block-cache hit returns bytes no checksum checks again,
  ZFS's page-cache finding in mantle's metadata; cached blocks are verified on serve at a sampled
  rate whose cost is measured, and a block that fails is dropped and read again and the failure
  attributed (node.md §5.6).
- **The block cache keeps RocksDB's policies.** HyperClockCache is lock-free on hits, the property
  mantle asks of every cache (gateway.md §5), and the conversion keeps RocksDB's behaviour, so
  the engine does not take the policy simulation mantle's own caches run; its size is its share of
  the node's division of cache memory by miss-ratio curves (node.md §2.5), sampled the same way.
- **Constants** that are format facts are kind `format` in constants.md with their RocksDB line;
  option defaults the engine inherits are not format and are set from note 12 §2's models or
  cited, never silently inherited (24 §1.19; CLAUDE.md §4).

## 4. Phases

Each phase ends on a tree that passes the gates and is committed on its own. A phase is done
when its RocksDB tests are ported and pass and its differential checks against the oracle pass.
P1–P15 are 24 §3.1, which lists each phase's test files with their counts and its checks:

## 5. Dependencies

| Need | Crate | Why |
|---|---|---|
| CRC-32C, masking's CRC, combination, extension | `mantle-crc` (`crc-fast`) | mantle's own CRC; `crc32c_extend` was added to it for RocksDB's `crc32c::Extend` |
| XXH32, XXH64, XXH3-64, XXH3-128 | `twox-hash` (feature `xxhash32` enabled for P1) | the released algorithms RocksDB vendors as xxHash 0.8.1 (24 §1.2) |
| XXPH3 (the XXH3 preview) | none: ported from util/xxph3.h | no crate implements the preview (24 §5 R1) |
| Snappy, LZ4 block, zlib raw deflate | `snap`, `lz4_flex`, `miniz_oxide` (pure Rust), from P4 | 24 §2.4 |
| ZSTD with dictionaries, training and streaming | `zstd` / `zstd-sys`, from P3 | see below |

**ZSTD.** No pure-Rust ZSTD encoder has dictionary training, and RocksDB's ZSTD-compressed
tables and WALs need it on the write side (24 §5 R9). The engine uses the `zstd` crate, which
builds the reference C library (BSD-3-Clause, allowed by `deny.toml`). mantle already builds and
cross-lints vendored C for AWS-LC (crypto.md; `scripts/check-targets.sh` cross-builds
aws-lc-sys's C and assembly for every target), so a C codec is a build of the same class, not a
new one; unlike the RocksDB binding it needs no C++ and no libclang. The codec is called behind
an unwind boundary (CLAUDE.md §1), and its inputs are bounded by the block and frame sizes the
engine already checks.

**Ported tests** (`crates/engine/tests`): util/coding_test.cc 19 of 19; util/crc32c_test.cc 8 of
8; util/hash_test.cc 16 of 16, the `Hash128`/`BijectiveHash` tests included because the SST
unique ID is built from those functions (24 §1.12); util/slice_test.cc 2 of 13. Of
slice_test.cc's other 11, seven move to the phases whose utilities they test (`PinnableSliceTest`
×3 to P8, `SmallEnumSetTest` ×3 to P6, `BitFieldsTest` to P9) and four test C++ facilities the
conversion replaces (`StatusTest.Update` by typed errors, `UnownedPtrTest` by
references, `SemaphoreTest` ×2 by `std::sync`). In `MathTest.BitOps`, `BitwiseAnd` (a C++
operand-width rule) and `ConstexprFloorLog2` have no Rust counterpart; the rest runs over Rust's
ten integer types of up to 64 bits, and `BitOps128` over `u128`. Proptest round trips cover every
coding form and check that no input makes a decoder panic or claim more bytes than it was given.

**Golden vectors.** `tests/golden/p1_gen.cc` is compiled outside the repository against the
unmodified RocksDB sources (util/hash.cc, crc32c.cc, crc32c_arm64.cc, xxhash.cc, coding.cc and
the header-only functions; `ComputeBuiltinChecksum*` copied verbatim from table/format.cc, which
otherwise links most of RocksDB). It prints 50 records: every hash, checksum and CRC form over
input lengths 0–4,096 (with several seeds, and with every byte's high bit set for the
sign-extension trap), and 4,096 random draws each for FastRange, the bijective hash, the context
modifier, masking, every varint and prefix-varint encoding, and decoding of random byte strings.
Each record stores the FNV-1a digest of each window of 32 outputs (110 KB in all,
`tests/golden/p1.txt`), so a mismatch names the function and the lengths it lies in.
`tests/golden.rs` recomputes all 50 and matches.

**Mutation checks.** Each of these single changes makes at least one test fail: XXPH3's tail
reads for 4–8 and 9–16 bytes, its middle byte for 1–3, its long-input last stripe, its mid-size
secret offset, its empty-input result, and its seeded long-input secret; `Hash`'s tail bytes
zero-extended instead of sign-extended; the XXH3 block checksum without its last-byte modifier;
the context modifier without the offset's upper half; the CRC mask's rotation; accepting a
varint32 overflow; the bijective hash's length term; the file checksum's byte order; FastRange64's
result; and the 9-byte prefix varint's marker byte.

**Open.** `twox-hash` and `crc-fast` are called directly, as mantle-s3 and mantle-crc already
do, not behind an unwind boundary: their one-shot paths index only within lengths they derive
from the input. The golden vectors were generated on aarch64 macOS; the x86_64 run of the same
program (the SSE 4.2 CRC kernel) is for the corpus work before P4.
