# The engine against RocksDB and SplinterDB on each supported target, with the cache-loan fix

2026-11-12, mantle `6398ad28` (branch validate-targets-2: main `87ab09e1`, rustix 1.1.6, and the
cache-loan fix of [2026-11-11-wrong-reads.md](2026-11-11-wrong-reads.md)). Carries
[2026-11-06-targets.md](2026-11-06-targets.md) forward. Supported targets: Linux and Windows on
x86_64 and aarch64, macOS on aarch64 (the owner: macOS x86_64 is not supported).

**Question.** On each supported target, does the engine hold 4-5x over RocksDB and SplinterDB on
fills, gets and seeks at 10M and 100M keys, and do metadata replication and transfer work?

## How it ran

The owner's harness (`benchmark-results/mantle-splinterdb-20261013`: `inside7.sh`,
`build-inner.sh`, `splinter_bench.c`, `bench-image.Dockerfile`), as 2026-11-06 ran it: on Linux in
its container, on macOS by `mac_williams.py` (the same design and flags; SplinterDB's I/O is
Linux-only, so macOS has no SplinterDB arm). Arms interleaved in a Williams order, each case's
rusage kept beside its output, its store removed after. Every arm: 16-byte keys, 100-byte values,
seed 301, a fill of NUM puts, 1M gets, 1M seeks of 10 rows, one client, no WAL, no compression,
64 MiB memtables.

- mantle: `benches/ranges.rs DB NUM 1 1000000 256 16 1000000 10 --rocks-seed=301 --shard-client
  --segments --machine-memory`, a release build with no diagnostic code; each case's values checked
  against the fill's oracle and its reopened store verified key by key.
- `rocks`, `rocks16`, `rocks32`: `db_bench` 11.8.1 (`abeebd963`), 256 MiB, 16 GiB and 32 GiB block
  cache, `--max_background_jobs` at the cores.
- `sdb16all`: `splinter_bench` over SplinterDB `7d607b11`, 16 GiB cache, every other core in the
  background.

### Every parameter and its source

| Parameter | Value | Source |
|---|---|---|
| Keys | 10M and 100M | Cited: the owner's rule, judge at 100M by default and at 10M. |
| Key and value size | 16 B, 100 B | Cited: `db_bench`'s own defaults at 11.8.1 (`tools/db_bench_tool.cc`: `key_size` 16, line 410; `value_size` 100, line 359), the owner's harness README's workload. |
| Gets, seeks, rows a seek | 1M, 1M, 10 | Cited: the owner's harness README (2026-10-13), the workload every arm runs (`db_bench`'s defaults would be a read for every key and seeks of 0 rows, lines 335 and 366). |
| Seed | 301, MT19937-64 | Cited: the owner's harness README (db_bench's key streams). |
| Memtable | 64 MiB | Cited: RocksDB's default `write_buffer_size` (`include/rocksdb/options.h:191`, `64 << 20`); `splinter_bench.c` and mantle's bench set the same. |
| WAL, compression | off | Cited: the owner's harness README; matched controls, since the ranges bench writes no WAL and mantle does not compress. |
| Block cache | 256 MiB, 16 GiB, 32 GiB | Swept: the three are a sweep of the comparator's cache (the tables give the lead at each). 256 MiB is the ranges bench's own fixed cache (its command line's budget); 16 GiB is derived, the smallest power of two above 100M rows (100M × 116 B = 11.6 GB; 12-13 GB measured, 2026-11-06); 32 GiB is research/58's and research/66's comparator. |
| `--max_background_jobs` | the cores the container has | Derived: every core, as mantle's pool takes every core (`inside7.sh`), not RocksDB's default of 2 (`options.h:900`). |
| SplinterDB cache | 16 GiB | As `rocks16`: the same derivation. |
| SplinterDB background threads | 1 memtable thread; every other core but the inserter's and that one's | Cited and derived: one memtable thread for one inserter is SplinterDB's rule (one per ten inserters, `splinterdb.h` lines 81-84); the normal threads take the rest of the CPU as RocksDB's jobs and mantle's pool do (`inside7.sh`), past the rule's 1-2 per inserter (lines 85-89). |
| Container memory cap, box | the box's `MemAvailable` when the run starts | Derived: what the box can give without swapping (proc(5), `/proc/meminfo`), read once the lock is held, just before the run, and written in the lane's log. 2026-11-06's 32 and 48 GiB were that run's own choice and are not used. |
| Container memory cap, aarch64 lane | 28 GiB (this run) | **Not derived**: 2026-11-06's figure, carried over for the 10M batch above. A rerun takes the VM's `MemAvailable` at its start, as the box does. |
| CPU set | box: CPUs 8-15; aarch64 lane: the VM's 14; macOS: the whole machine | Cited: Ada's rule for the box (benches on CPUs 8-15); elsewhere every core the machine has. |
| fd limit | each machine's own default (r718 excepted, above) | Cited: the owner's rule not to change descriptor limits. |
| Rounds | 4 at each size | Derived: one Williams cycle for four arms (`inside7.sh`: n rounds for an even count n), so each arm follows each other arm equally often; more cycles where an effect needs an A/A. |

A ratio is the median of each round's own ratio, with its range. Every case counted exited 0 and
found the same gets (632,048 at 10M, 631,247 at 100M). A busy host is the norm; no case was dropped
for load.

### macOS aarch64 at the Mac's own fd limit: main does not fill 100M

One 100M mantle case of the same binary (`ranges` `9fe024fb`, 6398ad28, r718's arguments) on the
same Mac at a kiln shell's own limits (soft 10,240, hard unlimited; no `ulimit -n` change), load 2,
its descriptors sampled with `lsof -p` every 2 s (`~/mantle-validate-harness/fd-check-*`):

| at | segments | descriptors |
|---|---|---|
| 2 s | 12 | 1,866 |
| 5 s | 22 | 4,357 |
| 7 s | 25 | 4,658 |
| 9 s | 27 | 5,076 (the last sample) |
| 11 s | 31 | `Too many open files (os error 24)`: "read a store page span ahead", opening `range-0.store.24` |

It ended in its fill, exit 1, with no rate. Descriptors grew about 188 a segment, as 2026-11-06 found
on Linux x86_64 at 2,048 (§ The descriptors): each of the 32 maintenance workers' device handles
opens each new segment for itself, so the limit is reached at a segment count that the cores and
the limit decide, not the platform. r718's 100M figures above therefore hold only with the limit
raised; at the Mac's own limit, 100M does not run on 32 cores. Its fix (hyper-block, one open file
shared among a handle's duplicates, `2026-11-06-targets-hyper-block-fd.patch`) waits on Ada's word.

At 10M the same check passed (exit 0, store verified on reopen): its descriptors peaked at 3,524
at 18 segments. Its one round beside r718's four mantle rounds with the limit raised:

| 10M mantle | fills/s | gets/s | seeks/s |
|---|---|---|---|
| at 10,240, n=1 | 3,968,587 | 2,673,298 | 678,702 |
| r718, raised, median (range), n=4 | 6,192,398 (4,044,611-6,931,200) | 2,991,467 (1,631,965-3,281,432) | 726,244 (673,186-793,772) |

Gets and seeks are within r718's own spread; fills are just below its slowest round, against a
spread of 1.7x among r718's own four, so one round does not tell the limit's effect from the
rounds' own: no open was refused, which is the only way a limit can cost a case.

## Defects found and fixed

- **Wrong answers at 100M under memory pressure (macOS, any target).** A page cache adopted a
  loan another cache had lent: fixed in `f961e054` and `9e5939ff`, three tests that fail without
  it, measured in [2026-11-11-wrong-reads.md](2026-11-11-wrong-reads.md).

## Open

- `clients::bench_log_runs_the_same_threads_at_ten_and_a_hundred_times_the_replicas` failed once in
  three gate runs on adacachy: an OS's thread count still holds a thread its joiner has joined
  (Linux `Threads:` 81,088 of 200,000 joins; macOS `proc_pidinfo` about 152,000 of 200,000; Linux
  tasks without `PF_EXITING` 0 of 400,000; macOS `task_threads` less dead threads 4-5 of 200,000).
  The count is hyper-block's; the fix belongs in hyper-raft, the owner to say how.
- The descriptors (2026-11-06 § The descriptors): every case from here runs at its machine's own
  default limit (the box's container default, Docker Desktop's on the aarch64 lane, 10,240 in a
  shell on a Mac), and a case that fails at it is recorded with its limit, peak descriptors and
  segments. One 100M mantle case on adas-mac-studio.local-2 at 10,240 is to run once that Mac is
  free.
